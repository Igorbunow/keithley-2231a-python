# H02 — защищённый профиль без нагрузки

Предыдущие аппаратные запуски на старой версии кода: первая попытка H02 — **FAIL**,
исправленный повтор — **PASS**; оба отчёта:
[`2026-10-25T213651.354322Z_H02_qualification.md`](hardware_reports/2026-10-25T213651.354322Z_H02_qualification.md).
`*IDN?` вернул firmware `1.04-1.04`, затем `1.04-0.01`; очередь ошибок оставалась
`0, "No error"`. Профиль был установлен, OFF-биты всех каналов = 0. Оператор
подтвердил физические OFF и уставки 1.00 V / 0.100 A на всех каналах. Библиотека
теперь аварийно останавливает применение профиля при изменении identity.
Офлайн-регрессии **48/48 PASS**. См. [отчёт исправленного PASS](hardware_reports/2026-10-25T214134.648837Z_H02_qualification.md).
H01 на текущем общем пути повторно пройден read-only, все ответы очереди ошибок были
`0, "No error"`, все выходы OFF подтверждены оператором; [новый отчёт](hardware_reports/2026-10-26T145345.082772Z_H01_qualification.md).
Подготовка H02 входит в подписанный коммит, который предшествует этому повтору.

Сценарий: `tests/hardware/profile_stage.py`; регистрация и операторские gates:
`tests/hardware/qualification.py`; offline-проверки: `tests/offline/test_qualification.py`.
В `identity()` добавлена проверка неизменности полного ответа `*IDN?` в пределах
подключения. При расхождении профиль не должен записывать настройки; это проверено
офлайн. В первом H02 firmware field различался между запросами; в повторе оба ответа
были `1.04-0.01`. Причина исходного позднего FAIL — runner сравнивал identity только
после применения профиля; guard теперь находится в библиотеке до конфигурационных
записей. Код ошибки прибора в обеих попытках не зафиксирован (очередь равна нулю).

Команды и семантика сверяются с [официальным руководством 077100401](https://download.tek.com/manual/077100401_Referencemanual.pdf),
раздел 5, Source/Output/System и Status model. При обнаружении несовместимости с
прошивкой — останов, исправление библиотеки и отдельный допуск повтора; обхода ошибки нет.

## Подключение и параметры

- CH1, CH2, CH3 выключены. Силовые клеммы свободны: без нагрузки, DUT и перемычек.
- Электронная нагрузка отсоединена от всех выходов, INPUT OFF. Режим и значение не задавать.
- На панели проверить `Output Recall = Off`. Сетевой выключатель Keithley доступен.
- Связь: проверенный CP2102 USB–TTL, `/dev/ttyUSB3`, 9600 8N1; один владелец порта.
- Все каналы: уставки **1.00 V / 0.100 A**, максимальная устанавливаемая величина
  **4.00 V**, программный current cap **0.500 A**. Реальный токовый лимит PSU задаётся
  `CURR 0.100`; отдельного аппаратного ограничения тока 0.500 A не устанавливается.
- `VOLT:LIM` ограничивает программируемое напряжение, не заменяет независимую OVP.
  Панель не блокируется через RWLOCK.

Выходы остаются OFF. При ошибочном ON после успешной установки уставок — до 1 V / 0.1 A,
0.1 W на канал. В рамках программных caps — до 4 V / 0.5 A, 2 W на канал, 6 W суммарно.
До установки профиля или при отказе ограничений паспортная возможность прибора —
30/30/5 V, 3 A на канал, суммарно 195 W. Точность аналогового измерения здесь не проверяется.

## Последовательность и SCPI

1. REM, идентификация, очередь ошибок, OFF-биты всех каналов и независимый режим.
2. Снимок **каждого** CH до изменения: выбранный канал, V/I, `VOLT:LIM`/state,
   выход, timer state/delay. Ненулевой код ошибки запрещает продолжение.
3. Для каждого CH проверить запрет ON через API без активного профиля: запрос должен
   завершиться исключением **до любой отправки SCPI**.
4. Через публичный `apply_profile()` применить профиль, оставляя выходы OFF.
5. `verify_profile()` и независимое чтение каждого CH: V/I, cap/state, выход, таймер,
   внутренние измерения U/I. Все реальные ответы сохраняются с временными метками.
6. Для каждого CH отвергнуть V=-0.01/4.01/NaN и I=-0.001/0.501/Inf до SCPI.
   После применения профиля ON не вызывается.
7. `emergency_off()`, чтение OFF всех каналов, выбор CH1 и проверка выбора, повторное
   чтение OFF, очередь ошибок, LOC, закрытие порта. Итоговые безопасные уставки сохраняются.
8. Отдельное подтверждение физических OFF оператором, отчёт и STOP перед H03.

Порядок последовательности задают публичные методы `apply_profile()` и
`verify_profile()` библиотеки. `H02Scope` разрешает только профильные SCPI-записи
и нужные readback-команды; driver trace и фактические ответы сохраняются в evidence.
Offline-регрессия сравнивает полный wire trace с общей трассой драйвера.
Разрешённые записи (все остальные, включая ON, блокируются):

```text
SYST:REM
OUTP 0
OUTP:SER 0
OUTP:PARALLEL 0
OUTP:TRAC 0
INST:NSEL 1 / 2 / 3
OUTP:TIM:STAT 0
VOLT 0
CURR 0
VOLT:LIM 4.00
VOLT:LIM:STAT 1
CURR 0.100
VOLT 1.00
SYST:LOC
```

После каждой записи, кроме LOC, выполняется `SYST:ERR?`. Код обязан быть 0; исходная
170 в H02 также означает FAIL. `*CLS` не используется, ошибки сохраняются в evidence.
Очередь дополнительно читается после снимков и перед LOC. LOC не имеет ответа;
проверка очереди после него в этот сценарий не входит.

Допуски относятся только к цифровым уставкам: ±0.0049 V и ±0.00049 A;
cap — ±0.0049 V; limit state=1; timer state=0; channel output=0;
бит 3 каждого ISUM=0; Series/Parallel/Tracking=0. Данные внутреннего измерителя
только фиксируются, без заявления о точности или независимой электрической проверке.

Один проход до 180 s. При ошибке — останов настроек, на известной живой связи только
попытка `OUTP 0`, проверка ошибок/OFF и LOC. Внутренний обработчик библиотеки может
предпринять более раннюю попытку OFF; точный план блокирует незапланированные команды.
При отказе I/O — прекратить SCPI, закрыть порт, **UNKNOWN OUTPUT STATE**;
автоподключения и повторного прогона нет. Ручной останов — сетевой выключатель
Keithley, затем физическая проверка OFF всех каналов и INPUT OFF нагрузки.

## Команды после разрешения оператора

Сначала только offline и preview (порт не открывается):

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -v
python3 tools/hw_qualify.py preflight H02
python3 tools/hw_qualify.py run H02 --dry-run
```

До запуска аппаратного H02 должны быть рассмотрены эти результаты. Только после
отдельного разрешения аппаратной группы:

```bash
python3 tools/hw_qualify.py run H02 --execute --port /dev/ttyUSB3
```

Точный токен перед открытием порта:

```text
CONFIRM H02 INDEPENDENT ALL_OFF LOAD=DISCONNECTED V=1.00 I=0.100 VCAP=4.00 ICAP=0.500 RECALL=OFF
```

После успешного прохода — отдельная ручная проверка, затем:

```text
CONFIRM H02 CH1=OFF CH2=OFF CH3=OFF LOAD=OFF
```

Пройденные offline-проверки охватывают dry-run без открытия порта, отказ
неинтерактивного запуска и чужого токена, полный успешный trace, останов при 170,
таймаут без дальнейших SCPI, несовпадение cap, исходный ON и блокировку команды ON
до передачи, включая изменение IDN до начала записей. Они **SIM TESTED**; H02 прошёл
в указанном no-load профиле, но электрическая точность под нагрузкой не проверялась.
Если identity изменится в новом подключении, библиотека остановится до настроек.
После результата — STOP до H03.

При текущем повторе один запуск был заблокирован матричной проверкой: H01 PASS
ссылался на evidence за пределами bold-статуса. Ссылка перенесена внутрь статуса,
добавлена регрессия; весь offline-набор прошёл 86/86. Вызов без TTY был штатно
отклонён gate. Одна попытка не открыла UART: `/dev/ttyUSB3` появился в системе уже
после вызова, вслед за повторной регистрацией CP2102; SCPI не отправлялись. После
подключения адаптера повтор прошёл с сохранением исходной H02-авторизации.
