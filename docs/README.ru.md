# keithley-2231a-python — библиотека управления Keithley 2231A-30-3

[English](../README.md) | [**Русский**](README.ru.md)

**Открытая Python-библиотека для трёхканального лабораторного источника питания Keithley 2231A-30-3:** SCPI через USB–TTL UART, перспективный Ethernet-мост UART–TCP, защищённые профили, очередность включения, сбор измерений, статистика, ВАХ и координация нескольких приборов.

**Версия 0.2.0 · Python 3.10+ · [MIT](../LICENSE) · независимый проект, не являющийся официальным продуктом Keithley/Tektronix.**

> **Экспериментальная версия — аппаратная квалификация ещё не завершена.** В меню испытанного Keithley указаны Main 1.04 / Aux 0.01; поле revision в сырых ответах `*IDN?` возвращало как `1.04-1.04`, так и `1.04-0.01`. Библиотека записывает revision, но не привязывает к нему совместимость. Остальные ограничения и результаты смотрите в [матрице проверки](VERIFICATION.ru.md). Новая версия прошивки всё равно требует отдельной аппаратной оценки.

## Возможности

- Три канала: **CH1/CH2 0–30 В, 0–3 А; CH3 0–5 В, 0–3 А**, суммарная номинальная мощность до 195 Вт.
- Независимое управление каналами; режимы Series, Parallel и Tracking CH1/CH2 с защитой от случайного переключения в процессе работы.
- **Series и Parallel требуют физических внешних соединений силовых клемм!** Прибор не переключает проводники внутри себя по команде SCPI. Соответствующие команды настраивают режим измерения/управления, а не устанавливают перемычки. Перед настройкой обязательно выключить все выходы и проверить подключение по руководству.
- Неизменяемые профили: максимумы U/I по каждому каналу, ожидаемый CV/CC, аппаратные ограничения напряжения и проверка показаний.
- **Профиль полного паспортного диапазона:** `Profile.unrestricted()` без дополнительных пользовательских ограничений, но в пределах **30/30/5 В и 3 А**; это не обход защит и не «сырые» SCPI-команды.
- **Профиль только питания:** `access='power_only'`. Уставки замораживаются после применения профиля. Фиксированная `power_sequence` задаёт порядок включения и автоматический обратный порядок отключения. Когда порядок задан, произвольно включать отдельные каналы запрещено.
- CSV-журнал, минимум/максимум/среднее/среднеквадратичное отклонение, расчёт А·ч и Вт·ч по фактическому времени опроса.
- Пошаговое снятие ВАХ и подключение внешних мультиметров; многоприборные сценарии планируются в отдельном проекте.
- UART `SerialTransport` или TCP `TcpTransport` по IP/домену и порту для будущего микроконтроллерного моста. Это **не** встроенный Ethernet интерфейс прибора и не VISA/VXI-11.

## Важные ограничения и безопасность

1. Разъём DB9 на задней панели Keithley — **TTL UART, а не обычный RS-232**. Использовать преобразователь соответствующего логического уровня, не подключать стандартный ±RS-232 напрямую. Настройки: 9600 бод, 8N1.
2. **У блока питания двухпроводное подключение силового выхода, без удалённого Kelvin sense.** При необходимости точного U на нагрузке измерять его отдельным DMM на клеммах устройства.
3. **Внешние перемычки Series/Parallel обязательны.** Программная команда не выполняет внутреннюю перекоммутацию выходов! Менять силовые провода только при отключённых выходах, проверять полярность/сечение/токи и схему изготовителя.
4. Режимы **CV/CC переключаются автоматически** по условиям нагрузки. Указание `expected_regulation='cv'` или `'cc'` означает *требовать соответствующий результат измерения*, а не «перевести в принудительный режим».
5. При обрыве USB/TCP программное `OUTP 0` может не дойти! Ни блокировка панели, ни опрос профиля не заменяют предохранитель, внешнюю OVP/OCP, аппаратную блокировку или независимый watchdog. Для ответственных/автономных испытаний нужны физические средства отключения.
6. Перед работой проверь на панели прибора **Output Recall = Off**, чтобы после восстановления сетевого питания выходы неожиданно не включились снова.
7. Источник **не умеет поглощать ток**, то есть не заменяет электронную нагрузку и не предназначен для разряда батареи. Показания А·ч — заряд, **отданный источником**. Не подключать непосредственно заряженный аккумулятор как нагрузку.
8. Испытания ВАХ диода требуют ограничительного резистора и корректного ограничения тока; миллиамперное разрешение самого источника недостаточно для измерения токов утечки в микроамперах.

[Официальное руководство Keithley, SCPI и режимы каналов](https://download.tek.com/manual/077100401_Referencemanual.pdf).

## Идентификация источника и версия прошивки

Библиотека проверяет производителя и модель, но не привязывается к версии firmware.
Сырая строка `instrument_id` сохраняет поле revision из `*IDN?`. Если к компьютеру
подключено несколько одинаковых источников, задайте ожидаемый серийный номер: при
несовпадении библиотека откажется применять профиль до записи настроек.

```python
psu = Keithley2231A(SerialTransport('/dev/ttyUSB1'), expected_serial='12345678')
print(psu.identity())       # исходный *IDN?, включая revision
print(psu.instrument_key)   # кортеж производитель/модель/серийный номер
```

Без привязки не передавайте `expected_serial`. В отчётах аппаратных проверок
записывайте версию из меню и сырое поле `*IDN?`; другая прошивка не блокируется кодом,
но требует отдельной квалификации поведения. На проверенном экземпляре меню показывает
Main 1.04 / Aux 0.01; в raw `*IDN?` наблюдались revision `1.04-1.04` и `1.04-0.01`.

## R3.2 — Контроль целостности профиля

`verify_profile()` проверяет профиль синхронно. `verify_every_s` — порог
проверки в `read_channel()` и интервал для **явно запускаемого** монитора;
сам параметр не запускает фоновый опрос. Если приложение не опрашивает
каналы и не вызвало `start_profile_monitor()`, периодической защиты нет.

```python
psu.start_profile_monitor()  # только после apply_profile; интервалы не гарантированы
try:
    # Разрешённые операции приложения
    ...
finally:
    psu.stop_profile_monitor()  # запрос остановки + ожидание окончания потока
print(psu.profile_monitor_running, psu.profile_monitor_error)
```

Монитор запускается только по запросу; он использует тот же транспорт,
блокировку SCPI, `verify_profile()` и общую обработку отказов. Интервал
отсчитывается **после завершения предыдущей проверки** и может удлиняться
из-за медленного SCPI. При отклонении монитор останавливается, фиксирует
ошибку, снимает armed и вызывает уже существующую попытку OFF с проверкой
ответа. Если соединение неопределённо, повторных команд нет и состояние
выходов **НЕИЗВЕСТНО**. `emergency_off()` инициирует остановку монитора;
`close()` ждёт его завершения до закрытия транспорта. Перед заменой профиля
монитор необходимо явно остановить. Программный поток не является аппаратным
watchdog / OVP / OCP и не гарантирует мгновенную реакцию. На реальном приборе
данный механизм пока не переквалифицирован.

## R3.4 — Переходы топологий и достоверность CV/CC (SIM TESTED)

При применении **любого** профиля (Independent/Tracking, Series, Parallel)
драйвер проверяет фактический режим `OUTP:PARALLEL?` самого источника, а не
только запомненный Python-профиль. Если Parallel включён, до команды
`OUTP:PARALLEL 0` обязательно отправляется `OUTP 0` и проверяется
`OUTP:STAT:ALL? = 0`. При неподтверждённом OFF смена режима и запись новых
уставок запрещены; обработчик отказа может отдельно попытаться отправить
аварийный OFF, но без подтверждения нельзя утверждать, что источник выключен.
Это программная проверка последовательности, а не аппаратное измерение
состояния силовых клемм.

Согласно [официальному руководству](https://download.tek.com/manual/077100401_Referencemanual.pdf)
(§3, Combine Off, стр. 3-8), при выходе из комбинированного режима требуется
ручная перекоммутация. `confirmed_wiring` остаётся заявлением оператора и
**не доказывает физически** отсутствие старых перемычек. Проверять и изменять
подключения разрешено только при безопасно отключённых выходах.

В официальной таблице статусов (§5, стр. 5-29–5-30) бит 2 регистра OPER
обозначает `CAL` (калибровочные вычисления). При нём библиотека выдаёт
`regulation='UNKNOWN'`, оставляет исходные значения OPER/QUES и не приписывает
режиму достоверный CV/CC. Противоречащие друг другу OPER/QUES также остаются
UNKNOWN. При требовании `expected_regulation='cv'`/`'cc'` недостоверность
вызывает существующую обработку нарушения профиля.

Проверка `VOLT:LIM:STAT?` не доказывает независимую аппаратную OVP.
Для Series/Parallel по имеющимся H09/H10 есть специфические ограничения;
ограничение суммарного напряжения библиотекой — **программное**. Новых
аппаратных наблюдений R3.4 нет; они запланированы отдельно на R3.5.

## Общая сессия и диагностический режим

`output_states()` читает состояния всех трёх выходов до и после применения профиля.
Драйвер сам проверяет identity и при необходимости входит в Remote, не изменяя
уставки и не включая выходы. Обычный API и диагностика используют общий диспетчер,
блокировку, учёт Remote/Local и обработку ошибок связи.

Output Recall и Save Last настраиваются с панели: руководство не описывает SCPI
доступ к ним. Драйвер не может обеспечить Recall Off до запуска прибора.
Для чтения восстановленных выходов вызовите `output_states()` перед
`apply_profile()`, который намеренно выключает все выходы.
[Процедура H06 Output Recall](H06_OUTPUT_RECALL.ru.md) использует новые сессии с
привязкой к serial и записывает состояние после старта до команды выключения.

По умолчанию диагностика выключена. `debug=True` разрешает `diagnostic_query()` и
`diagnostic_write()`. `debug_trace=callback` получает трассу команд и ответов с
обезличенным serial в identity; `debug_wire_trace=callback` — фактические байты UART
только для status-команд, без байтов identity.

Без обхода диагностические `VOLT`/`CURR` проходят обычный `set_channel()` и проверку
профиля. Для намеренного теста аппаратного лимита нужен отдельный флаг
`debug_bypass_profile=True`. Он относится только к диагностическим записям:
обычный `set_channel()` сохраняет soft-проверки даже при включённом флаге.

```python
# Existing debug-enabled instance, validated profile and all outputs OFF.
psu.diagnostic_write('INST:NSEL 1')
psu.debug_bypass_profile = True
try:
    psu.diagnostic_write('VOLT 4.51')  # Approved 4.50 V limit test only.
    reply = psu.diagnostic_query('SYST:ERR?')
finally:
    psu.debug_bypass_profile = False
```

Обход снимает ограничения профиля для диагностических записей. Он не снимает
запрет работы после сбоя связи, единоличное владение сессией и допуски адаптера
испытаний. Флаг не включается автоматически. При ошибке или прерывании обмена
состояние связи фиксируется как неопределённое; автоматического reconnect/retry нет.
`debug_adapter` добавляет политику испытания к общему механизму; прямые отправки
через адаптер вне диспетчера драйвера запрещены.


## R3.3 — Достоверность состояния выходов при отказах (SIM TESTED)

`output_states()` возвращает словарь булевых состояний **только после успешного
чтения выходов**. `False` означает полученный ответ OFF, а не невозможность
прочитать состояние. При неудачном чтении метод выбрасывает исключение, не
возвращает неполную карту и не подставляет `False` вместо UNKNOWN.

Некорректный числовой, булев или целочисленный ответ регистра/выбора
канала, повреждённый формат SCPI-ответа либо неожиданная идентификация другого
прибора фиксирует неопределённость соединения, снимает `armed` и запрещает
дальнейшие команды, включая восстановление ранее выбранного канала и
повторную попытку OFF. Обрыв связи и прерванный обмен обрабатываются так же. Если ответ корректен, но уставки/состояния не совпадают,
сохраняется общий маршрут попытки отключения с контрольным чтением.

**При `UNKNOWN OUTPUT STATE` считать выходы потенциально включёнными.**
Не повторять `emergency_off()` через повреждённое соединение и не рассчитывать,
что `close()` отключает выходы. При возможности и безопасности выключить выход
физической панелью прибора; иначе изолировать нагрузку независимым разъединителем
или interlock. Независимо проверить отсутствие напряжения подходящим измерителем,
проверить схему и только после этого создавать **новую** транспортную сессию.
SIM-тесты не доказывают фактическое отключение нагрузки. Аппаратные испытания
R3.3 ещё не проводились.

Обработка SCPI-ошибок (R2.3): `check_errors()` читает **одну** запись
`SYST:ERR?`. При корректном ненулевом коде активный профиль блокируется,
затем предпринимается отключение с проверкой фактического состояния выходов.
`output OFF confirmed` сообщается только после подтверждения чтением;
без него статус — `UNKNOWN OUTPUT STATE`. Некорректный ответ может означать
потерю синхронизации, поэтому соединение блокируется **без дополнительных
команд и повторов**. Если активного профиля нет, чтение ошибки не меняет
состояние выходов. Сейчас это SIM TESTED, новая аппаратная проверка не выполнена.

H01–H05 переведены на этот механизм и общие проверки `tests/hardware/common.py`.
Исторические аппаратные отчёты относятся к записанным в них версиям исходников.
Повторная квалификация общего пути выполнена для H01–H05, включая H04-Powered;
H05 имеет аппаратный статус PASS в пределах описанной схемы и оговорок. Дальнейшие
этапы указаны в [матрице квалификации](hardware_reports/qualification_matrix_2026-10-25.md).

## Workaround статусов CH3 и ограничения

CH3 доступен через обычные профили и методы `set_channel(3, ...)`,
`output(3, ...)`, `read_channel(3)`. На испытанном приборе (меню Main 1.04 / Aux 0.01)
OPER возвращает **8** как в CV, так и в CC: бит ON присутствует,
а документированные биты режима отсутствуют. Поканальный QUES корректно возвращает
**1 (CV)** и **2 (CC)**. Библиотека принимает однозначный режим из одного condition-
регистра, если у другого биты режима пусты. Отдельное включение workaround не нужно;
статусы для CH3 не подменяются.

```python
# Existing armed profile; this call does not enable the output.
reading = psu.read_channel(3)
print(reading.enabled, reading.regulation, reading.regulation_source)
print(reading.operation_status_mask, reading.questionable_status_mask)
# Observed ON/CV case: True, 'CV', 'questionable'; raw masks 8, 1.
```

Поле `Reading.regulation_source`: `'operation'`, `'questionable'` или `'both'`,
если режим включённого выхода определён; `None` для OFF, UNKNOWN или пропущенной
проверки режима. `enabled` независимо читается через `CHAN:OUTP?`; проверки
целостности ON/OFF используют бит ON в OPER, работавший в наблюдавшихся прогонах CH3.
Доставка команды и пустая очередь ошибок сами по себе не подтверждают выход или режим.
Оба condition-запроса должны завершиться успешно; ошибки связи по-прежнему приводят
к аварийной реакции. Противоречивые или неоднозначные режимы дают UNKNOWN;
`expected_regulation='cv'/'cc'` по-прежнему вызывает trip при несовпадении или UNKNOWN.
CV/CC определяется нагрузкой и уставками U/I, а не принудительным выбором через профиль.
Сырые маски сохраняются без изменения.

Ограничения: паспортный диапазон CH3 — **0–5 В, 0–3 А**, активный профиль может
сужать его. Физически наблюдались независимые CV при 4 В / 0.500 А, CR 40 Ом и CC
при 4 В / 0.250 А, CR 12 Ом, индивидуальные ON/OFF и чтение уставок. Это не
квалификация полного диапазона, таймеров CH3 и всех последующих этапов.
Резервное подтверждение CV/CC через OPER на этой прошивке отсутствует.
Новое поле источника и дополнительные регрессии — **SIM TESTED**
(66/66 offline-тестов прошли); само определение режима через QUES уже наблюдалось
на физическом приборе. Новое поле отдельно аппаратно не проверялось.

В [руководстве](https://download.tek.com/manual/077100401_Referencemanual.pdf),
разделы 5-20/21 и status model, групповые event/summary-регистры не дают полного
текущего CV/CC всех трёх каналов одним ответом. Используются поканальные запросы
`...ISUM1/2/3:COND?`; групповой event-запрос их не заменяет.
Пример `Acquisition.sample()` уже опрашивает все три независимых канала последовательно,
с отдельными временными метками; это не атомарный снимок. Новая групповая команда
не предполагается. См. [физическую диагностику](hardware_reports/2026-10-26T005733.649705Z_H03_qualification.md)
и [матрицу](VERIFICATION.ru.md). Результат проверки соответствия руководству H03
остаётся PARTIAL до уточнения производителя.

## Установка

```bash
# После создания репозитория на вашем GitHub
# git clone https://github.com/<ВАШ-АККАУНТ>/keithley-2231a-python.git
cd keithley-2231a-python
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
python -m unittest discover -s tests -v
```

Тесты запускаются **без прибора**. Для построения графиков дополнительно: `python -m pip install -e '.[plot]'`.

### Первая аппаратная проверка — только чтение

```bash
python examples/probe.py --port /dev/ttyUSB1
```

Пример проверяет идентификатор и состояния, не устанавливает напряжение и не включает выходы. Поддержку дополнительных запросов проверь по результатам этого запуска и руководству, **не переходи сразу к управлению нагрузкой**.

## Применение профиля

```python
from keithley2231a import Keithley2231A, SerialTransport, Profile

with Keithley2231A(SerialTransport('/dev/ttyUSB1')) as psu:
    psu.apply_profile(Profile.from_json('examples/safe_3ch.json'),
                      confirmed_wiring='independent')
    psu.verify_profile()
    psu.set_channel(1, voltage=1.2, current=0.1)
    # После проверки подключений на стенде:
    # psu.output(1, True)
```

**Обязательное подтверждение физической схемы:** перед применением профиля
Independent или Tracking вручную проверьте отсутствие **внешних** перемычек
Series/Parallel между CH1 и CH2, затем передайте
`confirmed_wiring='independent'`. Для Series/Parallel после осмотра
соответствующих внешних соединений при всех выходах OFF передавайте
`confirmed_wiring='series'` или `'parallel'`. Это только заявление оператора:
библиотека не может физически определить наличие перемычек. Без правильного
подтверждения SCPI-команды **не отправляются**. При возвращении из Series
или Parallel обе перемычки должны быть сняты вручную — отключение режима
командой SCPI не удаляет проводники.

**ВНИМАНИЕ:** `apply_profile()` всегда сначала отключает **все** выходы и перенастраивает источник. Не запускай его во время питания работающего устройства!

### Внешний режим Series

Для Series используется отдельный `SeriesProfile`. Физическую перемычку CH1−↔CH2+
устанавливают только при выключенных выходах и явно подтверждают при применении
профиля. У пары одна суммарная уставка U/I; `read_channel(1)` возвращает её с
меткой `CH1+CH2`, а индивидуальный `read_channel(2)` запрещён: на наблюдавшейся
прошивке выбор CH2 в Series алиасится на CH1. `combined_outputs(True,
confirm_all_channels_safe=True)` отправляет глобальный ON и может включить также
CH3; CH3 должен оставаться свободным либо отдельно безопасным. В наблюдавшейся
прошивке `VOLT:LIM:STAT?` общего Series-выхода выключен, поэтому суммарный лимит
профиля обеспечивает только программная защита, это не аппаратная OVP. Powered
runner проверен на реальном приборе для указанных CV/CC-точек; у чтения CC есть
оговорка о статусных битах прошивки, приведённая в матрице квалификации.

### Внешний режим Parallel

Для Parallel используется отдельный `ParallelProfile`. При выключенных выходах
соединить CH1+ с CH2+ и CH1− с CH2−, затем явно подтвердить
`confirmed_wiring='parallel'`. Пара читается через `read_channel(1)` с меткой
`CH1+CH2`; отдельное чтение или изменение уставки CH2 запрещено. `max_current`
задаёт суммарный ток пары (до 6 A) и записывается после выбора Parallel, пока
выходы выключены. На наблюдавшейся прошивке в этом режиме выключается аппаратный
voltage-limit пары: `max_voltage` ограничивает библиотека программно и не
является аппаратной OVP. `combined_outputs(True, confirm_all_channels_safe=True)`
включает глобальный выход, в том числе CH3. На реальном приборе H10 подтверждены
CV/CC до 0,3 А/1 Вт и точка CC 4,00 А / CR0,50 Ω / около 8 Вт; результаты и
оговорки приведены в [матрице](VERIFICATION.ru.md). Измерения на нагрузке и DMM
расходятся примерно на 47 мВ из-за падения на проводах между точками измерения.
Агрегатные измерения не доказывают распределение тока между ветвями.

## Профиль «только включить / выключить»

```python
from keithley2231a import Profile, ChannelProfile, PowerStep

profile = Profile(
    'digital-board',
    channels=(
        ChannelProfile(3.3, 0.15, initial_voltage=3.3, initial_current=0.10),
        ChannelProfile(5.0, 0.25, initial_voltage=5.0, initial_current=0.20),
        ChannelProfile(3.3, 0.10, initial_voltage=0.0, initial_current=0.05),
    ),
    access='power_only',
    power_sequence=(PowerStep(1, 0.0), PowerStep(2, 0.5)),
)
# psu.apply_profile(profile, confirmed_wiring='independent')  # сначала все OFF
# psu.power_on()              # CH1, затем через 0,5 с CH2
# psu.power_off()             # CH2, затем через 0,5 с CH1
```

Пока профиль активен, `set_channel`, `timer` и произвольная `sequence` запрещены. При заданной фиксированной последовательности `output(1, True)` также запрещён — использовать только `power_on()`/`power_off()`. Если список отсутствует, по умолчанию `power_on()` включает CH1→CH2→CH3, `power_off()` выключает в обратном порядке; отдельные выходы разрешены. **Это ограничение API данного процесса, а не аппаратная защита от другого приложения или панели прибора.**

## Подтверждение подключения аппаратного стенда (R3.5)

Токены физической схемы/нагрузки и финального OFF остаются обязательными. См. [R3_BENCH_CONNECTION_GATE.ru.md](R3_BENCH_CONNECTION_GATE.ru.md).
