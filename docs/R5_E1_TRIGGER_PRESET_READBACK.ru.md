# R5-E1 — цифровые SCPI-регистры триггерных уставок, программный этап

Статус: **SOFTWARE TESTED / REAL HARDWARE NOT RUN / TRIGGER ACTION NOT AUTHORIZED**.
Предыдущий аппаратный этап R5-D3 завершён: CV и CC STEP с внешней нагрузкой
прошли независимо на CH1, CH2 и CH3. Это доказательство **не распространяется**
на аппаратные триггеры.

## Основание

Официальное руководство Keithley 2231A-30-3, 077100401 (September 2014),
разделы 5-4, 5-12, 5-25 и 5-27:

- `VOLT:TRIG?`, `CURR:TRIG?`: чтение **отложенных** V/I-уставок выбранного канала;
  это не измерение выхода, не текущие `VOLT?`/`CURR?` и не `*TRG`.
- `*TRG` / `TRIG`: событие, способное применить отложенные уставки.
- `INST:COUP[:TRIG]`: выбор каналов, реагирующих на триггер. В таблице
  референса для `INST:COUP?` одновременно стоит аргумент и `Returns=None`,
  а пример записи `Inst:coup ch1.ch2` не устанавливает однозначную грамматику
  для запросов/множеств. Поэтому **не кодируем предполагаемый ответ** и
  не выдаём виртуальную симуляцию за знание поведения реального firmware.

Оригинал: https://download.tek.com/manual/077100401_Referencemanual.pdf

## Реализованный маршрут библиотеки

```python
from keithley2231a import Keithley2231A

# After operator-controlled application of an independent, control-access
# profile, with every physical output OFF:
registers = device.read_trigger_presets(2)
print(registers.channel, registers.voltage_v, registers.current_a)
```

Строго **CH1 / CH2 / CH3**, одинаковая логика, без ограничения одним каналом.
`TriggerPresetReadback` — неизменяемый объект. Метод требует применённый
независимый профиль с control-access, физически прочитанные OFF всех каналов,
`verify_profile()`, подтверждение `INST:NSEL?` и две последовательные проверки
`SYST:ERR?`. Повторной проверки профиля после чтения недостаточно для гарантии
от внешнего контроллера; аппаратное владение интерфейсом остаётся необходимым.

Два запроса идут **последовательно**; совместное snapshot/атомарность не
гарантируются. Диапазоны ответов: CH1/CH2 `0..30 V`, CH3 `0..5 V`,
все каналы `0..3 A`. Библиотека не навязывает *профильные* лимиты отложенному
регистру: он пока не применялся, а жёсткие паспортные границы проверяются.

Неправильные ответы, таймауты и неопределённая связь блокируют дальнейшие
посылки, без автоматического переподключения и без повторной отправки запроса.
Диагностический обход не даёт доступ к `INST:COUP`, записи `VOLT/CURR:TRIG`,
`*TRG`, `APPLy`, даже если пользователь включил debug mode.

## Что не выполнено

1. Нет **реального** подтверждения ответов `VOLT:TRIG?` / `CURR:TRIG?`
   на трёх каналах: capability `trigger_preset_readback` = `simulated_only`.
2. Нет квалификации регистра/формата `INST:COUP?` на firmware 1.04-1.04 /
   наблюдавшемся 1.04-0.01. Статус `documented_only`, запись заблокирована.
3. Нет `VOLT:TRIG`/`CURR:TRIG` write API, `*TRG` execute API, обновления
   профиля после trigger, доказательств временных задержек, одновременности,
   выключения или изменения выходов при каком-либо trigger-событии.
4. Ни тестовое значение регистра, ни `TRIG` не могут сами по себе разрешать
   включение выходов. Любая будущая аппаратная операция должна пройти через
   текущий guarded-driver и документированную схему операторского допуска.

## Контроль следующего аппаратного этапа (только после отдельного разрешения)

R5-E2: готовим безопасный OFF-only runner с отдельными пре-подтверждениями
для CH1/CH2/CH3, диагностикой firmware, оригинальным JSONL и независимым
аудитором. Первый проход — **только два read-only запроса**, без `*TRG`,
`INST:COUP` и выхода ON. После анализа и подтверждения протокола можно
по отдельному разрешению проектировать setter, coupling и test trigger effect,
с обязательным учётом того, что отложенные уставки могут сменить активные V/I.

Отсутствие глобального SCPI trigger не означает ограничение прибора:
пока ограничено **доказательство**, а не заявленная аппаратная возможность.
