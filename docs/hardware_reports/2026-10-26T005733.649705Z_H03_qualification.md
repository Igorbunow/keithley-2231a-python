## Review: CH3 status discrepancy localized at the instrument response boundary

Reviewed H03 functional disposition: **PASS with a non-blocking OPER status caveat**.
This diagnostic run’s strict raw runner outcome remains **PARTIAL** because it required
OPER CV/CC mode bits. Both CH3 CV/CC electrical comparisons and live front-panel
confirmations passed. The library returned the correct CV and CC modes from the
documented questionable condition bits. The instrument operation condition register
still omitted its documented mode bits. All **274** `SYST:ERR?` replies were
`0, "No error"`. Final operation conditions were 0/0/0, KEL103 INPUT read OFF, and
the operator confirmed all physical outputs OFF. No active runner remains.

Firmware: **1.04-1.04**. Source: base commit `95a5ef1c6f93ca5364924056acd21b97b4c4f90a`
committed source `2e8db9427e41e61a269ad5ffac381de559691817`.
Keithley CP2102 UART 9600 8N1; KEL103 V3.30 USB serial 115200 8N1. Independent
channels, no jumpers/DUT, load only on CH3. Caps 4.00 V / 0.500 A; CC current
setpoint 0.250 A. No calibrated external DMM was used; this is a load comparison.

* Every short and full operation query returned actual UART bytes `38 0a` (`8\n`)
  while CH3 was ON. Questionable replies were `31 0a` (CV) and `32 0a` (CC).
* The observed delay window, abbreviation choice and selected-channel dependence
  do not explain the result. CH1/CH2 remained OFF; selecting CH1 returned its
  `CHAN:OUTP?=0` without changing CH3's condition reply.
* Both CH3 ENAB masks remained 0; the preceding OFF probe also read all six
  per-channel OP/QUES enable masks as 0. No status mask or event register was written.
* The unknown CH1 questionable bit 4 (`16`) was also present at OFF. It is recorded
  without assigning an undocumented meaning; it is not used to explain CH3's mode.

The original software defect was reliance on operation status alone for regulation.
The existing driver correction has now been replayed on physical CH3 in CV and CC:
`read_channel()` reports the expected modes. This diagnosis required no additional
library fallback or fabricated mode bits. The H03 guard fix was also exercised:
its channel-specific ON authorization now precedes transmission. Its rejection
paths are **SIM TESTED**, not intentionally exercised on energized physical hardware.

**Conclusion:** the anomalous value originates in the device's SCPI response, before
library parsing. The internal cause (firmware defect versus a manual inaccuracy)
is **not proven**. Python cannot repair the instrument's internal condition register.
The independent OPER mode-bit comparison remains a documented manual-conformance caveat;
it does not block functional CH3 operation because QUES, API, display and load agree.
H04 was not executed in this run and remains NOT_RUN.

### Engineering consequence

Existing drivers' age and successful setpoint/measurement use do not demonstrate
that they ever checked the redundant operation mode bits. The reviewed code does
not establish that another author solved this exact discrepancy. The C driver's
questionable event query must not replace the documented, non-clearing per-channel
`STAT:QUES:INST:ISUM3:COND?` used in our physical CV/CC replay.

No additional library patch follows from these sources. Correct CV/CC reporting
through documented condition bits is already physically observed. Raw OPER3 is
preserved as 8; no bits are fabricated and no CH3-specific constant is substituted.
The remaining manual-versus-instrument discrepancy needs manufacturer clarification
or new discriminating evidence. H03 remains **PARTIAL**; this research does not
promote its conformance result or authorize H04. The manufacturer draft above has
**not been sent**.
