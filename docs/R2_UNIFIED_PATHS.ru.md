# R2 — аудит единых путей управления SCPI

Статус: **программная регрессия выполнена; аппаратная переквалификация ещё не проведена**.
R2.4 продолжает R2.1–R2.3; это рефакторинг, а не изменение возможностей прибора.

## Инварианты

1. `Keithley2231A._execute()` — единственный маршрут физических SCPI-команд. `_write()` и `_query()` используют `_dispatch_scpi()`; диагностический адаптер также не может послать команду минуя этот маршрут.
2. `set_channel()` использует общую валидацию диапазонов, шага и ожидаемых уставок для Independent, Series и Parallel. Режим Tracking имеет отдельную проверку *обоих* физических каналов, поскольку его семантика иная.
3. `output()`, `combined_outputs()`, `power_on()` и `power_off()` проверяют активный профиль и подтверждают прочитанное состояние; аварийное выключение идёт через `emergency_off()` и `_off_confirmed()`.
4. Все три процедуры применения профиля используют один `_disable_combined_modes()` (одинаковый порядок сброса SER → PARALLEL → TRAC) и один `_abort_profile_application()` при отказе. Последний делает **только попытку** `OUTP 0`: запись команды без readback **не считается подтверждением OFF**.
5. Объединённые профили используют общие `_verify_combined_outputs()` и `_verify_combined_ch3()`; специфические проверки суммарного напряжения/тока и аппаратных регистров Series/Parallel остаются раздельными намеренно.
6. Любой неопределённый ответ или транспортный сбой блокирует повторный обмен по этому соединению; после потери синхронизации никакие автоматические повторные команды не отправляются.

## Проверка R2.4

- Режимы `Independent`, `Series`, `Parallel`: SCPI-трассы применения профиля и последующей `verify_profile()` до и после R2.4 совпали побайтно на эмуляторе.
- Инъекция отказа в применение каждого из трёх профилей: снят `armed`, зафиксирован fault, `_profile` сброшен; попытка `OUTP 0` идёт через общий путь и не выдаётся за подтверждённое отключение.
- Инъекция изменения `VOLT:LIM` CH3 в обоих комбинированных режимах: одна проверка обнаруживает отклонение и переводит драйвер в fault.
- Программная регрессия: `tests.test_driver`, `tests.test_profiles_sweep_bench`, `tests.offline.test_bench_config`, `tests.offline.test_equipment_inventory`, `tests.offline.test_incremental_patch`. Результаты должны быть подтверждены в целевой среде; не маркировать новые аппаратные `HW VERIFIED` без измерений.

## Что R2 намеренно НЕ исправляет

- Физические перемычки при переходе обратно в Independent должны быть подтверждены оператором: исправление относится к R3.
- Программная проверка профиля не является непрерывным независимым аппаратным ограничителем: политика мониторинга — R3.
- После обрыва связи нельзя подтвердить выключение выходов; требуется отдельная аппаратная проверка безопасного поведения — R3.
- В объединённых режимах аппаратные лимиты и интерпретация CV/CC имеют особенности прошивки; требуются адресные проверки R3, без повторения всей исторической матрицы.
- Полное покрытие документированных SCPI-команд и универсальный высокоуровневый API относятся к следующим этапам R4 и R5.

## Правила выполнения на оборудовании

Данный патч **не требует автоматического включения выходов**. Если аппаратная квалификация затронутых функций будет запущена позднее, Codex сначала делает `inventory`, затем просит отдельное подтверждение для каждой физической конфигурации. Нельзя автоматически переключать внешние перемычки или считать отправленный `OUTP 0` доказательством отсутствия напряжения.

## Актуализация тестового пути после R3.5.64 (примечание, не изменение R2)

Историческая команда для `tests.test_profiles_sweep_bench` относится к состоянию R2.
После программного рефакторинга соответствующие проверки находятся в
`tests.offline.test_profiles_sweep_uart`: тесты управления выполняются через
production-драйвер и виртуальный UART; валидация данных остаётся обычным
unit-тестом. Исторические выводы R2 этим не переоцениваются.
