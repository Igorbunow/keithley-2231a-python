# R4.3-D/E: сервисные планы и безопасный симулятор — только OFFLINE (R3.5.45–46)

> **ОПАСНЫЕ ОПЕРАЦИИ. НЕ ИСПОЛЬЗОВАТЬ БЕЗ РЕАЛЬНОЙ НЕОБХОДИМОСТИ.**
> Отдельный сервисный путь предназначен для квалифицированного специалиста.
> На стадиях R3.5.45–46 никакого исполнения опасных SCPI-команд на аппаратуре нет.
> Все предлагаемые команды — только текстовые планы, а **не проверенные на
> прошивке 1.04-1.04 рабочие последовательности**.

## Граница доступа

* Обычный `Profile.from_json` не принимает сервисную схему; существующие
  `access=control|power_only`, `Profile.unrestricted()` и `debug=True` не дают
  сервисных полномочий.
* Сервисные права хранятся в **отдельном** JSON профиле с полем `mode: service`,
  точной моделью, серийным номером и явным списком `allowed_operations`.
  Значение пустого списка, wildcard и неопознанные имена запрещены.
* Одного разрешения в профиле **недостаточно**: создание каждого плана требует
  точного подтверждения, привязанного к виду операции, серийному номеру и
  SHA256 байтов сервисного профиля. Это **не аутентификация** и не
  криптографическая защита от злонамеренного Python-кода.
* `keithley2231a.service.ServicePlanner` не импортирует драйвер или Transport,
  не содержит методов исполнения, отправки SCPI либо подключения к порту.
* В основном драйвере через `_execute` блокируются основные команды сервиса
  даже при `debug_bypass_profile=True`. Но это **политика библиотечного API**:
  клиент с прямым доступом к UART, `._raw` или другим сторонним инструментам
  всё равно способен послать SCPI. Для критичных операций требуются внешние
  организационные меры и физическая изоляция.
* Будущий реальный `ServiceSession`, если он будет разработан, должен работать
  только в отдельном процессе, с операторской процедурой, блокировкой
  обычной сессии, привязкой USB/IDN/серийного номера, сроком действия
  согласия, неизменяемым журналом, предварительным и итоговым контролем OFF,
  запретом повторов после ошибки и запретом запуска из штатного API.
  **В R3.5.45 такого исполнительного слоя нет.**

## Покрытые имена разрешений (все только симуляционные)

| Имя права | SCPI / назначение | Риск |
|---|---|---|
| `self_test`, `wait_pending` | `*TST?`, `*WAI` | Самодиагностика, ожидание |
| `clear_events`, `reset_status` | `*CLS`, `STAT:PRES` | Потеря диагностических данных |
| `reset_settings`, `trigger_bus` | `*RST`, `*TRG` | Изменение состояния / триггер |
| `save_setup`, `recall_setup` | `*SAV n`, `*RCL n`, **n = 0…30** | Энергонезависимая запись / восстановление |
| `apply_channel` | `APPL CHx,V,I` | Изменение выходных уставок |
| `power_on_status_write` | `*PSC n` | **Форма записи в справочнике неоднозначна** |
| `calibration_unlock`, `calibration_lock` | `CAL:SEC OFF` / `CAL:SEC ON` | Открытие / закрытие калибровки |
| `calibration_voltage`, `calibration_current` | `CAL:VOLT:LEV` / `CAL:CURR:LEV` и данные | Изменение коэффициентов |
| `calibration_save`, `calibration_initialize` | `CAL:SAV`, `CAL:INIT` | Необратимая запись / сброс коэффициентов |
| `calibration_label` | `CAL:STR` | Изменение калибровочных сведений |

**Неизвестные и неуточнённые команды не принимаются как строки**; разрешение
означает право *составить* типизированный план, не право послать команду.
`*TST?` в заголовке справочника указан с `?`, но в таблице синтаксиса на
стр. 5-5 приведено `*TST` — несовпадение обязательно выяснить по сервисной
документации до включения реального исполнения. Аналогично таблица для
`*PSC` не объясняет аргумент записи. Статус обеих форм — **UNVERIFIED**.

## Пример (offline, без соединения с прибором)

Скопировать `config/service.example.json` в отдельный приватный файл,
заменить серийный номер на настоящий и явно перечислить только нужные права.
Не коммитить служебный профиль и пароли калибровки. Обычные профили не менять.

```bash
python3 tools/service_plan_offline.py \
  --service-profile /private/service.json \
  --operation self_test --show-required-ack

# Полученную точную строку подтверждения оператор указывает с --ack:
python3 tools/service_plan_offline.py \
  --service-profile /private/service.json \
  --operation self_test --ack 'SERVICE PLAN self_test <SERIAL> <HASH12>'
```

Никакого `--execute` / аппаратного режима утилита не предоставляет.
Серийный номер и SHA связывают утверждение с конкретным текстом профиля.

## Калибровка: порядок работ и границы источника

Руководство [Keithley 2231A-30-3, Reference Manual 077100401, §5,
стр. 5-7…5-9](https://download.tek.com/manual/077100401_Referencemanual.pdf)
документирует команды и **порядок точек**, но не даёт достаточного полного
эталонного протокола настройки: температурной выдержки, перечня оборудования,
конкретных опорных уставок для каждой точки, схем включения, допусков при
настройке и допустимого состояния выходов. Не заменять этим текстом
фирменную процедуру adjustment/service. Пока такая процедура не получена,
**калибровку на реальном приборе не начинать**.

1. Уполномоченный специалист устанавливает причину калибровки и сначала
   проводит *проверку характеристик*, а не корректировку. Сохранить дату
   предыдущей калибровки, идентичность прибора, версию ПО, состояние и
   показания до вмешательства. Проверить документацию на конкретную ревизию.
2. Подготовить поверенные/калиброванные эталоны напряжения и тока, подходящую
   нагрузку/шунт и безопасную схему соединения; отключить DUT. Отдельно
   подтвердить отсутствие перемычек между выходами и сторонних контроллеров.
   Соблюдать электрические пределы и тепловой режим. **Не считать подтверждение
   `CHx=OFF` защитой от включения выхода сервисной командой.**
3. При наличии полной официальной процедуры установить, каким образом
   требуется снять блокировку `CAL:SEC` и проверить ответ состояния. Пароль
   не записывать в коде, JSON, тестовых логах или artefact ZIP.
4. Для **каждого нужного канала**: последовательность точек напряжения строго
   **P1 → P2 → P3 → P4**. Перед передачей значения обеспечить установленное
   производителем состояние и внешний независимый эталонный замер, затем
   регистрировать замер как данные соответствующей точки.
5. Аналогично для тока: **P1 → P2**. Учитывать действительные измерения,
   а не копировать номинал или примеры из SCPI-справочника. Пример
   `30.0002V` на стр. 5-8 показывает, что калибровочные данные и пользовательские
   уставки нельзя валидировать одним и тем же ограничителем.
6. `CAL:SAV` допускается **только после** независимой проверки всех значений,
   полной записи evidence и отдельного решения специалиста: это сохранение
   коэффициентов в энергонезависимую память. `CAL:INIT` — исключительная
   аварийная операция со смыслом сброса коэффициентов и отдельным правом;
   **не использовать для подготовки к калибровке**.
7. Восстановить защиту `CAL:SEC ON`, вернуть выходы в подтверждённое OFF,
   выполнить независимую проверку точности для CH1/CH2/CH3 и сохранить
   результаты «до / после» с неопределённостью и прослеживаемостью эталонов.
   При расхождениях не маркировать прибор как прошедший калибровку.

**Статус R3.5.45**: offline compiler / policy tests; **HW NOT_RUN для всех
сервисных команд**, включая чтение `*TST?`. Числовые ограничения в компиляторе
лишь предотвращают опечатки; они **не являются заводскими допусками
калибровки** или разрешением подать напряжение/ток.


## R3.5.46: симулятор выполнения сервисного сценария (без транспорта)

**Никакого доступа к прибору:** `ServiceSimulator` не принимает `Transport`,
COM/USB/TCP-адрес, экземпляр драйвера или готовый произвольный план. Внутри
создаются **только фиктивные записи** `SCPI_NOT_SENT`, `FAKE_REPLY` и
`FAKE_ERROR_CHECK`. Статус `SIMULATED_PASS` означает успех модели, **не
HW PASS**, отсутствие физического воздействия или корректность синтаксиса
команды в конкретной прошивке. Подтверждения `FakeBench` задаются оператором
как сценарий для модели и **не являются реальным readback**.

Перед каждой модельной операцией заново проверяются:

1. Точная модель/серийный номер у фиктивного стенда и в сервисном профиле;
   все три фиктивных выхода OFF, Independent, Recall OFF, idle, link known.
2. Наличие именно данного права в сервисном профиле и отдельного
   подтверждения `SERVICE PLAN ...`, связанного с SHA256 исходного JSON.
3. Дополнительный одноразовый для текущего процесса `SIMULATE ONLY ...
   SEQ=N` (после каждой операции номер увеличивается); для каждой операции
   риска **critical** — ещё и `SIMULATE CRITICAL ... SEQ=N`.
4. Порядок сервисного автомата. Для калибровочных точек нужен предварительный
   **фиктивный** `calibration_unlock`; каждая пара (канал, тип калибровки)
   полностью выполняется не более одного раза. До `calibration_save` у
   каждого затронутого канала должны присутствовать обе завершённые
   последовательности напряжения P1–P4 и тока P1–P2. Это консервативное
   **правило симулятора**, а не утверждение о заводской сервисной процедуре.
5. `calibration_initialize` требует отдельного свежего сценария и отдельного
   critical-подтверждения. Она **никогда не вызывается на приборе**.
6. Даже если изменение не было сохранено, фиктивное `calibration_lock`
   допустимо для моделирования возврата защиты, но такой незавершённый
   цикл получает `SIMULATED_ABORTED`, а не успешную калибровку.

Любой внедрённый синтетический `timeout`, `scpi_error` или `output_on` помечает
сессию как ошибочную **без дальнейших фиктивных SCPI и повторов**. Дальнейшее
моделирование в этой сессии блокируется; для исследования отказа создают
*новый* фиктивный сценарий. Это не схема автоматического восстановления
реального прибора после сбоя: фактический статус выхода/блокировки должен
проверять специалист независимо.

### Быстрый пример (строго программный)

```bash
# В service.json нужно явно разрешить, например, только self_test.
python3 tools/service_simulate_offline.py \
  --service-profile /private/service.json --operation self_test \
  --show-required-acks

# Точные строки из предыдущего вывода подставляются в оба аргумента:
python3 tools/service_simulate_offline.py \
  --service-profile /private/service.json --operation self_test \
  --ack 'SERVICE PLAN self_test ...' \
  --sim-ack 'SIMULATE ONLY self_test ... SEQ=1'
```

Для `critical` понадобится ещё аргумент `--critical-ack`, а набор всех
операций в одном состоянии тестируется через Python `ServiceSimulator`.
У CLI **нет** флагов `--execute`, `--config`, `--port`, `--connect` и нет
обнаружения USB. Приватный профиль, пароль или фактические калибровочные
данные **не отправлять в Git**. Моделируемые команды могут быть **не
проверены на синтаксис прошивки** и никогда не должны копироваться в
терминал для исполнения без официальной сервисной методики.

**Статус R3.5.46: SIMULATED ONLY / HW NOT_RUN.** Ни одна сервисная команда
не была передана реальному Keithley.
