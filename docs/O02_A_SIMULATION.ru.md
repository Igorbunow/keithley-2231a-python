# O02-A: изолированная симуляция двух независимых PSU (R3.5.33)

**Статус:** `SIM TESTED / HW NOT_RUN`. Этот этап **не** подключает и не конфигурирует второй реальный Keithley, не включает физические выходы и не выполняет аппаратную синхронизацию. Он не переносит аппаратную квалификацию O01 на O02.

## Назначение и граница безопасности

`experiments.o02_dual_psu.dual_offline` — отдельная модель двух сессий с синтетическими идентификаторами `SIM-*` и адресами `sim://*`. Класс `DualOfflineSimulation` принимает только два объекта **точного типа** `SimulatedSource`, а не наследников и не реальные `Keithley2231A`, UART/TCP-порты, функции отправки SCPI или произвольные адаптеры.

Симулятор моделирует не физическое напряжение, а упорядоченные состояния `ON`, `OFF`, `UNKNOWN` и отказоустойчивое завершение двух сессий. Даже когда симуляция сообщает `PASS`, это означает **только прохождение модели**, а не безопасный OFF реальных приборов. `O02 --execute` и `--allow-o02-on` не существуют. Для O02-A не предусмотрены схемы межсоединений, общие минусы, выходные перемычки, реальные измерения DMM, источник внешнего триггера или программы аппаратного включения.

## Симулируемая процедура

1. До любых модельных команд проверить две различные пары serial/endpoint, структуру двух низкоэнергетических уставок и целостность области идентификаторов `SIM-`/`sim://`.
2. Независимо прочитать идентичности обоих симуляторов и начальные OFF. Ошибка первого **не пропускает проверку второго**. Не отправлять команды неизвестному или неподтверждённому устройству.
3. Требовать **два отдельных** identity-bound токена `CONFIRM O02-A SIM ...`, по одному на A и B; токен первого не разрешает включение второго.
4. В модели активировать сначала A (0,50 В / 40 мА), прочитать ON; затем B (0,75 В / 50 мА), прочитать ON. Только в симуляции два разных, не соединённых между собой источника могут находиться ON одновременно; ни одно из этих значений не является инструкцией к подключению реального второго PSU.
5. При успехе или любом исключении выполнить независимые **однократные** попытки OFF B и A, затем отдельно прочитать состояния. Если связь с одним симулятором стала `UNKNOWN`, не выполнять по нему дальнейших команд, но всё равно попытаться выключить другой по известной исправной сессии.
6. Записать `JSONL` **после** попыток OFF во временный файл, проверить его и лишь затем атомарно опубликовать без перезаписи уже существующего. `PASS` разрешён лишь при обоих явных `OFF`, корректном порядке идентификаций/подтверждений и сохранении доказательств. Валидатор перечитывает файл, проверяет последовательность, симуляционный маркер, временные метки и содержимое итоговой строки. Запись с неизвестным состоянием никогда не повышается до PASS.

## Offline-команды (без оборудования)

Запуск успешной симуляции (путь к **новому** файлу, существующий файл не перезаписывается):

```bash
python3 tools/o02_offline.py --evidence /tmp/o02_a_nominal.jsonl
```

Симулировать потерю подтверждения включения B: ожидаемый выход с кодом `2`, `ABORTED`, `A=OFF`, `B=UNKNOWN`:

```bash
python3 tools/o02_offline.py --evidence /tmp/o02_a_lost_b.jsonl \
  --fault-source B --fault enable_lost_after_on
```

Другие сценарии: `identify_wrong`, `identify_lost`, `preflight_lost`, `enable_stuck_off`, `enable_verify_stale_off`, `off_lost`, `off_stuck_on`, `off_verify_lost`, а также `--initially-on A/B`.

Полные тесты:

```bash
PYTHONPATH=src:tests:tests/hardware python3 -m unittest discover -s tests -v
python3 -m compileall -q src tests tools
```

**Проверить сохранённую JSONL можно программно:** `experiments.o02_dual_psu.dual_offline.audit_dual_simulation_evidence(path)`. Валидатор обнаруживает подмену статуса, псевдопорта, идентичности, номера события, порядка, часов, разрешений и последнего OFF. Он **не** является криптографической подписью; при необходимости защиты от умышленной правки нужен отдельный digest/signature.

## Отложенные O02-B/C — НЕ текущий roadmap

- O02-B: отдельно спроектировать строго host-timed последовательный координатор с доказательством границ времени, потери/старения измерений, независимыми интервалами и без заявления об одновременной выборке.
- O02-C: отдельная электрическая карточка MCU/trigger, с проверкой уровней и изоляции, затем согласование аппаратов, схемы проводов, внешних аппаратных interlock. Пока нет подтверждения второго PSU и триггерного стенда: **`HW NOT_RUN`**.

О02-А — исследовательский черновик в `experiments/`, не часть устанавливаемой библиотеки. O02-B/C заморожены до появления отдельного проекта верхнего слоя.

В отличие от O01, успешный O02-A не представляет собой завершённую HW-квалификацию и не допускает её автоматической регистрации как `HW VERIFIED`.
