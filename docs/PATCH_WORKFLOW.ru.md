# Передача изменений через incremental patches

Обмениваемся не копиями проекта, а двумя файлами на один логический этап:

- `STAGE.patch` — Git unified patch в формате `git diff --binary --no-renames`;
- `STAGE.stage_paths.txt` — **точный** набор изменяемых путей относительно корня репозитория, по одному на строку.

Главный помощник: `Scripts/apply_incremental_patch.sh`. Утилита устанавливается
один раз, а затем используется для всех последующих патчей. Она не выполняет
тесты, не подключается к оборудованию и **не создаёт коммиты**.

## Применение

Из корня репозитория, сохранив файлы патча и манифеста в `~/Downloads`:

```bash
Scripts/apply_incremental_patch.sh --check \
  ~/Downloads/STAGE.patch ~/Downloads/STAGE.stage_paths.txt
Scripts/apply_incremental_patch.sh \
  ~/Downloads/STAGE.patch ~/Downloads/STAGE.stage_paths.txt

git diff --cached --check
git diff --cached --stat
```

`--check` не меняет рабочее дерево и индекс. Обычный вызов применяет патч и
добавляет в индекс **только** его перечисленные файлы. Уже подготовленные в
индексе изменения сохраняются; незакоммиченные изменения отслеживаемых файлов
в рабочем дереве запрещены, чтобы не затереть чужую работу. Непривязанные к
патчу untracked-файлы остаются на месте.

Проверки и аппаратные испытания выполняются **после** применения патча. Только
при успешной проверке предлагается конкретный commit message. При провале
теста сохраняем состояние и отчёт, затем выпускаем следующий небольшой патч.

## Генерация патча

Если изменены уже отслеживаемые файлы, создавайте патч через
`git diff --binary --no-renames` до помещения изменений в индекс. Если изменения
уже staged, используйте `git diff --cached --binary --no-renames`. Новые файлы
нужно включить в индекс для генерации Git patch.

Записывайте в `STAGE.stage_paths.txt` только изменяемые файлы, не каталоги;
названия должны **точно совпадать** с `git apply --numstat -z`.

Переименования оформляйте как удаление + создание: скрипт намеренно отклоняет
Git rename/copy патчи, чтобы не допустить неоднозначного stage manifest.

## Важные ограничения

- При ошибке проверки патч не применяется. При ошибках ввода-вывода во время
  `git apply` / `git add` возможна частичная запись: перед повторным вызовом
  смотрите `git status` и не используйте автоматический `reset`.
- Применение патча не доказывает работу на аппаратуре. Эти проверки проводятся
  по отдельному протоколу с подтверждением оператора.
- `.gitignore` исключает локальные настройки стенда и диагностические журналы;
  они не должны попадать в stage manifest.
