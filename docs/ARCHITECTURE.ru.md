# Архитектура keithley-2231a-python

[English](../ARCHITECTURE.md) | [Русский](ARCHITECTURE.ru.md) · [Главная](README.ru.md)

## Принципы

Библиотека разделяет транспорт команд, управление конкретным блоком Keithley, неизменяемые профили и сбор измерений. Многоприборную оркестрацию выносим в будущий отдельный проект. **Программная проверка профиля не является независимой электрической защитой.** Изменения режима на передней панели, команда другого контроллера или обрыв связи могут оставить источник в нежелательном состоянии.

```text
 Приложение / испытательный стенд / примеры
                 |
        voltage_sweep / Acquisition
                 |
            Keithley2231A
                 |
       Profile / PowerStep
                 |
         Transport.write/query
           /          \
   SerialTransport  TcpTransport
        UART        TCP-UART мост
           \          /
        Keithley 2231A-30-3
```

## Модули и зоны ответственности

| Модуль | Назначение |
| --- | --- |
| `transport.py` | UART 9600 8N1 и прозрачная TCP-передача строк SCPI |
| `profile.py` | `ChannelProfile`, `PowerStep`, `Profile`, загрузка JSON и валидация |
| `device.py` | SCPI-команды, ограничения, включение/выключение, профили, таймеры, состояния |
| `monitor.py` | Статистика по каналам, CSV, А·ч и Вт·ч по фактическому времени |
| `sweep.py` | Пошаговые измерения ВАХ, внешние DMM, выключение при завершении |
| `tests/` | Программный эмулятор. **Не подтверждает работу реального прибора** |

## Жизненный цикл

`Created → apply_profile() → Armed/OFF → explicit output ON → optional start_profile_monitor() → stop_profile_monitor() → OFF`. При любом выявленном отклонении библиотека помечает устройство как неисправное и **пытается** выполнить `OUTP 0`. При пропадании связи эта попытка не гарантирует отключения.

`verify_every_s` не запускает периодический опрос без явного `start_profile_monitor()`. Фоновая проверка использует общую блокировку SCPI и общий механизм аварии; задержка проверок не ограничена. Это дополнительный контроль, не независимая защита.

`apply_profile` принудительно выключает все каналы, проверяет это, снимает программные режимы объединения, устанавливает аппаратные ограничения напряжения и уставки, считывает их и только затем разрешает дальнейшее управление. Применение другого профиля требует отключения и повторного вооружения (`emergency_off`, затем `apply_profile`).

`Profile.unrestricted()` означает **весь паспортный диапазон прибора**, а не возможность превысить паспортные параметры или обойти аппаратные ограничения. Профиль `power_only` после настройки разрешает только питание; изменение уставок, таймера, произвольной очередности и освобождение заблокированной панели запрещены. При наличии `power_sequence` включение идёт по списку, выключение — в обратном порядке. Если списка нет, можно включать каналы поодиночке; `power_on()` использует CH1→CH2→CH3.

**CV/CC не выбирается командой как принудительный режим.** Источник переключает стабилизацию согласно нагрузке; поле `expected_regulation` задаёт проверяемое ожидание.

## Физическое объединение CH1 и CH2

**Series/Parallel требуют физических внешних перемычек. Никакие SCPI-команды не выполняют внутренней перекоммутации выходов.** Подтверждение `confirmed_wiring` лишь фиксирует заявление пользователя. Оно не измеряет сопротивление перемычек и не проверяет полярность. При монтаже и изменении схемы все каналы должны быть отключены. Не забывать, что объединённые режимы меняют отображение измерений.

## Синхронизация и несколько приборов

Это задача отдельного будущего проекта. Здесь не создаём координатор чужих
приборов и не притворяемся, что программные отметки времени дают аппаратную
синхронность. Драйвер Keithley разрабатываем с декларацией возможностей и
высокоуровневым API для независимого использования. Ethernet-мост по-прежнему
требует одного управляющего клиента и отдельной политики отказа связи.

## ВАХ и измерения

`voltage_sweep()` требует выключенных остальных каналов, пошагово задаёт напряжение, ждёт установления режима, читает напряжение и ток, опрашивает при необходимости DMM и записывает CSV. По завершении пытается отключить все выходы. Источник не умеет поглощать ток: это не электронная нагрузка и не полноценный SMU. Для диода нужен правильно рассчитанный токоограничивающий резистор; для микроамперных токов необходим отдельный измеритель.

## Проверка и развитие

Каждая подтверждённая функция должна иметь протокол с коммитом, моделью прибора, прошивкой, конфигурацией нагрузки, ожидаемыми/фактическими ответами и результатом. CI подтверждает только программную симуляцию. См. [матрицу](VERIFICATION.ru.md), [процедуру](HARDWARE_TESTS.ru.md), [английскую архитектуру](../ARCHITECTURE.md).

## Единый путь SCPI

Обычные методы и явно включённая диагностика используют общий диспетчер
`_write`/`_query`. Адаптер политики испытаний оборачивает внутренний командный канал,
который запрещает отправки вне диспетчера. `_execute` выполняет фактический обмен,
ведёт Remote/Local, обезличивает трассу и фиксирует неопределённость связи.
Автоматические чтения ошибок адаптером также проходят через `_execute`.

По умолчанию `debug=False`. Диагностика разрешает исследовать сырые ответы,
сохраняя проверки профиля для voltage/current. Отдельный `debug_bypass_profile`
нужен для намеренных проверок лимита или tamper; обычный API сохраняет soft-защиту.
Трассировка байтов статуса реализована транспортом и включается драйвером только
в debug; внешние обёртки приватного `_serial` удалены.

Все политики этапов наследуют `StageAdapter` в `tests/hardware/common.py`.
В них остаются допуски команд/значений, лимиты времени и авторизация каналов.
Инициализация SCPI и последовательности драйвера в этапах не дублируются.
Общие проверки выходов, снимков настроек и операторские gates переиспользуются.
