# Повторная квалификация общего пути SCPI

Дата: 2026-10-26. Текущий результат: **SIM TESTED, 86 offline-тестов PASS**.
H01/H02/H03/H04/H04P/H05 на изменённом коде имеют **NOT_RUN / HW UNVERIFIED**.
Предыдущие отчёты сохраняются как доказательства для указанных в них ревизий.

## Что изменено

- Обычный API, диагностические команды и проверки очереди ошибок адаптером проходят
  через один механизм `_execute` в `Keithley2231A`.
- Драйвер ведёт identity, Remote/Local, выбранный канал, блокировку и отказ связи.
  Неопределённый обмен, включая прерывание запроса, запрещает последующие команды;
  автоматического повторного подключения нет.
- По умолчанию `debug=False`, `debug_bypass_profile=False`. Без обхода диагностические
  voltage/current проходят soft-проверки. С явно включённым обходом можно проверить
  отказ самого прибора. Обычный `set_channel()` продолжает соблюдать профиль.
- Все этапы используют `StageAdapter`, `require_outputs`, `channel_snapshot` и общие
  операторские gates из `tests/hardware/common.py` там, где они применимы.
- Удалены скопированные последовательности `command_plan`, отдельные реализации
  CheckedIO/StageIO/PoweredProfileIO/H05Transport и внешняя StatusWireTrace.
  Политики H01/H02/H03/H04/H04P/H05 задают только допуски и критерии своих сценариев.
- UART status-byte trace включается библиотекой через `debug_wire_trace`; прямого
  изменения приватного `_serial` в runner больше нет. Identity-байты не записываются.
- Каждый успешный offline-сценарий H01–H05 сравнивает все команды эмулятора с общей
  трассой драйвера. Эмулятор начинает в Local и отвергает неподготовленный обмен.

## Выполненные программные проверки

```sh
PYTHONPATH=src:tests:tests/hardware python3 -m unittest discover -s tests -v
python3 -m py_compile src/keithley2231a/*.py tests/hardware/*.py tests/offline/test_qualification.py examples/probe.py
git diff --check
```

Все 86 тестов прошли. Проверены нормальный/debug пути, отключённая диагностика,
soft-отказ без SCPI, явный обход с моделируемой ошибкой прибора 120 и неизменённой
уставкой, сохранение serial binding, отсутствие повторов после потери/прерывания
обмена, UART-трасса без identity, операторские паузы и все реализованные сценарии.
CLI dry-run H01/H02/H03/H04/H04P/H05 не открывал порты и не отправлял SCPI.
Результат модели аппаратного лимита не считается новым физическим измерением.

## Следующий физический шаг: H01

Перед изменением проводки проверить на приборах **CH1/CH2/CH3 OFF, KEL103 INPUT OFF**
и отсутствие напряжения. Затем:

1. Отключить силовые провода KEL103 от Keithley; INPUT оставить OFF. Режим и номинал
   нагрузки в H01 не используются. USB нагрузки можно оставить подключённым.
2. Отсоединить наконечники и земляные зажимы всех щупов TDS 3064B от источника.
3. Снять временное объединение отрицательных клемм, использованное в H05. Проверить,
   что все три выхода независимы, клеммы свободны, перемычек Series/Parallel и DUT нет.
4. На Keithley проверить Independent и Output Recall=Off. Выходы не включать.

Keithley: `/dev/ttyUSB3`, CP2102 `10C4:EA60`, USB–TTL, 9600 8N1.
Испытанный firmware: меню Main 1.04 / Aux 0.01; версия перечитывается, не блокируется
по конкретному revision. H01 не задаёт напряжение, ток, лимиты, таймер или ON/OFF.
Разрешены Remote/Local и выбор канала для чтения всех трёх снимков; исходный выбор
восстанавливается. Каждый ответ и извлечённая запись ошибки сохраняются.

При выключенных выходах ожидается отсутствие отдаваемой мощности. До применения
H02 ограничения ещё не установлены: паспортные пределы каналов 30/30/5 V, 3 A,
суммарно 195 W. При неопределённом состоянии использовать сетевой выключатель;
SCPI не считается гарантией отключения.

После подготовки схемы:

```text
CONFIRM H01 INDEPENDENT ALL_OFF LOAD=DISCONNECTED
```

```sh
python3 tools/hw_qualify.py run H01 --execute --port /dev/ttyUSB3
```

После H01 — проверка оператором всех OFF, review отчёта, предложение английского
сообщения коммита и ожидание согласования. Далее повторяются H02, H03 (все шесть
CV/CC точек), H04, H04P (soft/hard проверки и 21 powered-точка), затем H05.
Перестановка нагрузки и возврат схемы осциллографа требуют отдельных подтверждений.
Матрицы не повышаются до аппаратного PASS на основании offline-тестов.
