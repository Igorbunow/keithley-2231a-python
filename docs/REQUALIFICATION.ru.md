# Повторная квалификация общего пути SCPI

Дата: 2026-10-26. Текущий результат: **SIM TESTED, 95 offline-тестов PASS**.
H01–H04P повторно квалифицированы в текущем общем пути; H05 прошёл powered
последовательность с аппаратной регистрацией. Таймерная часть H06 прошла на приборе:
CH1/CH2/CH3 отключились за 3.051/3.063/3.056 s, повторное включение и финальный OFF
подтверждены. Output Recall после сетевого цикла ещё не проверялся. Подробности и ограничения приведены в
[матрице квалификации](hardware_reports/qualification_matrix_2026-10-25.md) и
[отчёте H05](hardware_reports/2026-10-26T190417.647970Z_H05_qualification.md).
Предыдущие отчёты сохраняются как доказательства для указанных в них ревизий.

## Что изменено

- Обычный API, диагностические команды и проверки очереди ошибок адаптером проходят
  через один механизм `_execute` в `Keithley2231A`.
- Драйвер ведёт identity, Remote/Local, выбранный канал, блокировку и отказ связи.
  Неопределённый обмен, включая прерывание запроса, запрещает последующие команды;
  автоматического повторного подключения нет.
- По умолчанию `debug=False`, `debug_bypass_profile=False`. Без обхода диагностические
  voltage/current проходят soft-проверки. С явно включённым обходом можно проверить
  отказ самого прибора. Обычный `set_channel()` продолжает соблюдать профиль.
- Все этапы используют `StageAdapter`, `require_outputs`, `channel_snapshot` и общие
  операторские gates из `tests/hardware/common.py` там, где они применимы.
- Удалены скопированные последовательности `command_plan`, отдельные реализации
  CheckedIO/StageIO/PoweredProfileIO/H05Transport и внешняя StatusWireTrace.
  Политики H01/H02/H03/H04/H04P/H05 задают только допуски и критерии своих сценариев.
- UART status-byte trace включается библиотекой через `debug_wire_trace`; прямого
  изменения приватного `_serial` в runner больше нет. Identity-байты не записываются.
- Каждый успешный offline-сценарий H01–H05 сравнивает все команды эмулятора с общей
  трассой драйвера. Эмулятор начинает в Local и отвергает неподготовленный обмен.

## Выполненные программные проверки

```sh
PYTHONPATH=src:tests:tests/hardware python3 -m unittest discover -s tests -v
python3 -m py_compile src/keithley2231a/*.py tests/hardware/*.py tests/offline/test_qualification.py examples/probe.py
git diff --check
```

Все 95 тестов прошли. Проверены нормальный/debug пути, отключённая диагностика,
soft-отказ без SCPI, явный обход с моделируемой ошибкой прибора 120 и неизменённой
уставкой, сохранение serial binding, отсутствие повторов после потери/прерывания
обмена, UART-трасса без identity, операторские паузы и все реализованные сценарии.
CLI dry-run H01/H02/H03/H04/H04P/H05 не открывал порты и не отправлял SCPI.
Результат модели аппаратного лимита не считается новым физическим измерением.

## Завершённые аппаратные этапы текущего общего пути

H01 read-only, H02 OFF-only, H03 шесть connected-load CV/CC точек, H04 OFF-only,
H04-Powered и H05 завершены в текущем runner. H02–H05 имеют отдельные аппаратные
отчёты и итоговые подтверждения OFF. H05 проверен при firmware field `1.04-1.04`;
этот факт документирует образец испытания и не ограничивает совместимость библиотеки.
Его последовательность `power_only` прошла с шестью фронтами, сверкой KEL103/PSU,
296 чистыми ответами `SYST:ERR?` и финальным физическим OFF. Оговорки о CH2 chatter и
общем минусе схемы приведены в протоколе и матрице.

Следующие аппаратные этапы H06–H12/O01/O02 остаются отдельными задачами; их статус
см. в матрице. Матрицы не повышаются до аппаратного PASS на основании offline-тестов.

## Исторический план повторной квалификации

H01 readback показал до изменения профиля: CH1 `2.20 V / 0.100 A`, CH2
`3.30 V / 0.100 A`, CH3 `4.40 V / 0.100 A`; на всех `VOLT:LIM=4.50 V`, limit
state=1, выходы и таймеры OFF. Эти значения проверены напрямую повторным чтением
всех каналов. H02 заменит уставки каждого CH на `1.00 V / 0.100 A`, предел — на
`4.00 V`, и задаст software current cap `0.500 A`; KEL103 остаётся отключённой.

Перед аппаратным запуском:

1. Keithley — Independent; CH1/CH2/CH3 OFF; свободные клеммы, нет DUT и перемычек.
2. KEL103 силовыми проводами не подключена, INPUT OFF; выбрать режим/значение не нужно.
3. На панели Keithley проверить Output Recall=Off и оставить доступным сетевой выключатель.
4. Проверить, что напряжение на выходных клеммах равно нулю. Никакие кабели для H02
   переставлять не требуется.

Keithley: `/dev/ttyUSB3`, CP2102 `10C4:EA60`, 9600 8N1; один владелец порта.
Все действия H02 остаются без нагрузки и без включения выхода. Ошибка или потеря
связи останавливает сценарий; при неопределённом состоянии использовать сетевой
выключатель и вручную проверить OFF.

После проверки схемы отдельное разрешение на запуск:

```text
CONFIRM H02 INDEPENDENT ALL_OFF LOAD=DISCONNECTED V=1.00 I=0.100 VCAP=4.00 ICAP=0.500 RECALL=OFF
```
