# Матрица подтверждения функций на оборудовании

[Русский](VERIFICATION.ru.md) | [English](VERIFICATION.md) · [Порядок испытаний](HARDWARE_TESTS.ru.md)

**Обозначения:** `HW VERIFIED` — подтверждено настоящим прибором с полным протоколом; `HW OBSERVED` — наблюдение на реальном приборе без полного протокола; `SIM TESTED` — проверено программным эмулятором; `HW UNVERIFIED` — работа на железе ещё не подтверждена; `PLANNED` — функция пока запланирована.

На данный момент известно реальное успешное подключение Keithley 2231A-30-3 с прошивкой **1.04-1.04** через USB–UART: команда `SYSTem:REMote` принята, `*IDN?` вернула корректную строку. **Это ещё не полный воспроизводимый протокол испытаний**, а подтверждённое наблюдение оператора. На другие команды этот результат не распространяется.

## Как перевести возможность в HW VERIFIED

Для каждой функции создать отчёт в `docs/hardware_reports/` по [шаблону](hardware_reports/TEMPLATE.md): дата, версия исходников/коммит, модель и прошивка, нагрузка, соединение, ожидаемые ответы, реальные ответы, проверка DMM/осциллографом, погрешности/оговорки. Серийные номера перед публикацией удалить или обезличить. Прежде чем считать результат пройденным, отдельно проверить ошибки связи/некорректные параметры, а не только штатную работу. Изменения версии библиотеки и прошивки требуют переоценки квалификации.

**Зелёные тесты GitHub Actions — только подтверждение логики на эмуляторе, не реального источника.** Библиотека не заменяет независимую аппаратную защиту.

## Подготовка квалификации — 2026-10-25

[Точная матрица H01–H12/O01/O02](hardware_reports/qualification_matrix_2026-10-25.md)
при подготовке содержала **NOT_RUN** для каждой новой аппаратной группы; текущая попытка H01 описана ниже. UART, `SYST:REM` и
`*IDN?` остаются **HW OBSERVED** на основании [наблюдения оператора](hardware_reports/2026-10-25_uart_idn_observation.md).
При подготовке доступа к физическому прибору не было.

Исходные offline-тесты: **31 passed**. После адресных регрессий: **46 passed**,
Python 3.13.5 / pyserial 3.5, `PYTHONPATH=src python3 -m unittest discover -s tests -v`.
Это только **SIM TESTED**. См. [аудит](hardware_reports/2026-10-25_offline_audit.md).

`tools/hw_qualify.py list`, `preflight H01` и `run H01` по умолчанию работают
без открытия порта. На этом этапе исполняемый сценарий есть только у H01,
с точным интерактивным подтверждением. Он меняет только remote/local,
опрашивает выбранный канал и ON-биты всех трёх каналов, извлекает одну запись
ошибки. Команд изменения выходов, уставок, топологии или таймеров нет.
Исполнение H02–H12/O01/O02 закрыто до разбора предыдущих доказательств,
паспорта нагрузки и отдельных карточек; результаты этих тестов остаются NOT_RUN.

На эмуляторе проверены точные разрешённые V/I и лимит напряжения, обнаружение
незапрошенного ON, поканальная проверка OFF, отключение унаследованных таймеров,
строгая проверка identity/bool и запрет повторного использования транспорта
после отказа. Включение Series/Parallel временно запрещено до квалификации
совмещённых уставок; неизвестные совмещённые уставки возвращаются как `None`.
Изменение уставок в Tracking пока недоступно. Документированной команды чтения
блокировки панели нет; обнаружение внешней разблокировки не гарантируется.
`VOLT:LIM` — максимум устанавливаемого напряжения, не независимая OVP по
измерению. Запуск таймера удалённым ON, совмещённые readback и всё электрическое
поведение остаются HW UNVERIFIED.

## Попытка H01 — 2026-10-26 МСК / 2026-10-25 UTC

**H01: ABORTED**; [обезличенные физические доказательства](hardware_reports/2026-10-25T210502.973378Z_H01_preflight.md).
Ревизия `99f2c442649eb7b357a0da603c81330028b6a475`, чистый checkout при запуске,
прошивка `1.04-1.04`, UART `/dev/ttyUSB1`, 9600 8N1, CP2102 `10C4:EA60`.
COM-01/02 остаются HW OBSERVED, теперь с записанной разрешённой попыткой. COM-03
получает **HW OBSERVED только для** `SYST:VERS?=1991.1`, `INST:NSEL?=1`,
поканальных operation conditions `0/0/0`, `OUTP:STAT:ALL?=0` и `OUTP:SER?=0`.
Другие запросы и поведение под напряжением остаются HW UNVERIFIED. Повышения
до HW VERIFIED нет.

На `OUTP:PARA?` возникло исключение I/O; ответ не записан. Исходные подробности
исключения runner не сохранил, поэтому неподдерживаемое сокращение — гипотеза,
а не доказанная причина. После сбоя не было чтения очереди ошибок, LOC,
переподключения или команд выходам. Порт закрыт; финальный физический OFF
ожидает подтверждения оператора. H02–H12/O01/O02 остаются NOT_RUN и требуют
отдельного разрешения.

### Исправление H01, ожидает повторной проверки — 2026-10-26

После H01 оператор увидел в меню прибора `170, Invalid command`. Последним
запросом был `OUTP:PARA?`. Синтаксис OUTPUT в руководстве — `PARallel`, но
пример непоследовательно использует PARA. Теперь библиотека посылает полное
`OUTP:PARALLEL` во всех записях/запросах; H01 использует то же имя. Эмулятор
отвергает спорную форму; **46 offline-тестов проходят**. Аппаратного повтора
ещё не было: H01 остаётся ABORTED, исправленная команда — HW UNVERIFIED.
Обновлённый H01 отдельно сохраняет исходную известную 170, требует финального
кода ошибки 0, фиксирует типы исключений и останавливается на любой новой
ошибке. H02 закрыт до устранения ошибки и успешного H01 с новым допуском.

### Повтор H01 PASS — 2026-10-26 МСК

[Физические доказательства и точная область проверки](hardware_reports/2026-10-25T211550.545588Z_H01_preflight.md).
Базовая ревизия `99f2c442649eb7b357a0da603c81330028b6a475` с незакоммиченным
исправлением имени Parallel; SHA256 исходников `6bb6eb7808af5dde318884bcb445b62257b087abc9625fa25c84d8d98bc25266`.
Прошивка 1.04-1.04, CP2102 UART 9600 8N1. Выполнены все 28 запросов;
`OUTP:PARALLEL?=0`; код ошибки в начале/конце 0; IDN и OFF-биты повторились.
Оператор подтвердил OFF всех трёх каналов, уставки панели 1 V / 0.1 A.

COM-01/COM-02 — HW VERIFIED для данного сценария UART/REM/IDN. COM-03 —
HW VERIFIED только для перечисленных запросов чтения выбранного CH1–CH3 и чтения OFF
всех каналов. Положительные ON/CV/CC,
применение caps, истечение таймеров, точность измерения и активные объединённые
режимы остаются HW UNVERIFIED. `VOLT:LIM?=30.1 V` при state=0 — наблюдение
исходного состояния CH1, а не безопасный включённый cap. Ошибка **запроса**
Parallel в этом сценарии устранена; команды установки ещё ожидают H02/H10.
H02–H12/O01/O02 остаются NOT_RUN. Коммит и следующий этап не выполнялись;
предыдущий протокол ABORTED сохранён.

### Дополнение H01 — чтение CH2/CH3

[Доказательства SCPI с временными метками](hardware_reports/2026-10-25T212311.676405Z_H01_CH2_CH3_readback.md).
Для запросов канал выбирался отдельно, после чего восстановлен CH1. На обоих
каналах прочитано `VOLT?=1 V`, `CURR?=0.1 A`, `CHAN:OUTP?=0`, таймер выключен.
OFF-биты всех каналов до и после равны 0; `SYST:ERR?` до и после вернул
`0, "No error"`. `VOLT:LIM?` CH2/CH3 показал 30.1 V / 5.1 V при state=0 — это
наблюдение, а не активная защита. Измерения PSU не калиброваны и не сверялись
с независимым прибором. Read-only снимок H01 теперь охватывает все три канала;
работа под питанием остаётся непроверенной.
