# Матрица подтверждения функций на оборудовании

[Русский](VERIFICATION.ru.md) | [English](VERIFICATION.md) · [Порядок испытаний](HARDWARE_TESTS.ru.md)

**Обозначения:** `HW VERIFIED` — подтверждено настоящим прибором с полным протоколом; `HW OBSERVED` — наблюдение на реальном приборе без полного протокола; `SIM TESTED` — проверено программным эмулятором; `HW UNVERIFIED` — работа на железе ещё не подтверждена; `PLANNED` — функция пока запланирована.

На данный момент известно реальное успешное подключение Keithley 2231A-30-3 с прошивкой **1.04-1.04** через USB–UART: команда `SYSTem:REMote` принята, `*IDN?` вернула корректную строку. **Это ещё не полный воспроизводимый протокол испытаний**, а подтверждённое наблюдение оператора. На другие команды этот результат не распространяется.

## Как перевести возможность в HW VERIFIED

Для каждой функции создать отчёт в `docs/hardware_reports/` по [шаблону](hardware_reports/TEMPLATE.md): дата, версия исходников/коммит, модель и прошивка, нагрузка, соединение, ожидаемые ответы, реальные ответы, проверка DMM/осциллографом, погрешности/оговорки. Серийные номера перед публикацией удалить или обезличить. Прежде чем считать результат пройденным, отдельно проверить ошибки связи/некорректные параметры, а не только штатную работу. Изменения версии библиотеки и прошивки требуют переоценки квалификации.

**Зелёные тесты GitHub Actions — только подтверждение логики на эмуляторе, не реального источника.** Библиотека не заменяет независимую аппаратную защиту.

измерению. Запуск таймера удалённым ON, совмещённые readback и всё электрическое
поведение остаются HW UNVERIFIED.

## Попытка H01 — 2026-10-26 МСК / 2026-10-25 UTC

**H01: ABORTED**; [обезличенные физические доказательства](hardware_reports/2026-10-25T210502.973378Z_H01_preflight.md).
Ревизия `99f2c442649eb7b357a0da603c81330028b6a475`, чистый checkout при запуске,
прошивка `1.04-1.04`, UART `/dev/ttyUSB1`, 9600 8N1, CP2102 `10C4:EA60`.
COM-01/02 остаются HW OBSERVED, теперь с записанной разрешённой попыткой. COM-03
получает **HW OBSERVED только для** `SYST:VERS?=1991.1`, `INST:NSEL?=1`,
поканальных operation conditions `0/0/0`, `OUTP:STAT:ALL?=0` и `OUTP:SER?=0`.
Другие запросы и поведение под напряжением остаются HW UNVERIFIED. Повышения
до HW VERIFIED нет.

На `OUTP:PARA?` возникло исключение I/O; ответ не записан. Исходные подробности
исключения runner не сохранил, поэтому неподдерживаемое сокращение — гипотеза,
а не доказанная причина. После сбоя не было чтения очереди ошибок, LOC,
переподключения или команд выходам. Порт закрыт; финальный физический OFF
ожидает подтверждения оператора. H02–H12/O01/O02 остаются NOT_RUN и требуют
отдельного разрешения.

### Исправление H01, ожидает повторной проверки — 2026-10-26

После H01 оператор увидел в меню прибора `170, Invalid command`. Последним
запросом был `OUTP:PARA?`. Синтаксис OUTPUT в руководстве — `PARallel`, но
пример непоследовательно использует PARA. Теперь библиотека посылает полное
`OUTP:PARALLEL` во всех записях/запросах; H01 использует то же имя. Эмулятор
отвергает спорную форму; **46 offline-тестов проходят**. Аппаратного повтора
ещё не было: H01 остаётся ABORTED, исправленная команда — HW UNVERIFIED.
Обновлённый H01 отдельно сохраняет исходную известную 170, требует финального
кода ошибки 0, фиксирует типы исключений и останавливается на любой новой
ошибке. H02 закрыт до устранения ошибки и успешного H01 с новым допуском.

Оператор подтвердил OFF всех трёх каналов, уставки панели 1 V / 0.1 A.

HW VERIFIED только для перечисленных запросов чтения выбранного CH1–CH3 и чтения OFF

### H02: первая попытка FAIL, исправленный повтор PASS — 2026-10-26

Подготовлен сценарий `apply_profile()` / `verify_profile()`: все каналы 1.00 V / 0.100 A,
V-cap 4.00 V, программный I-cap 0.500 A, выходы OFF, нагрузка отсоединена.
Runner отклоняет отклонения от плана команд до передачи и проверяет очередь ошибок
после каждой записи, кроме LOC. Подготовлены регрессии успешной последовательности,
ошибки 170, отказа I/O, несовпадения cap, исходного ON и запрета передачи ON.
Offline-регрессии прошли **48/48 SIM TESTED**. В первой аппаратной попытке `*IDN?`
вернул firmware `1.04-1.04`, а затем `1.04-0.01`; runner сравнил строки после применения
профиля, поэтому ошибочно поздно прервал H02. Очередь SCPI возвращала только
`0, "No error"`; все каналы остались OFF, оператор подтвердил OFF и уставки
1.00 V / 0.100 A. Библиотека теперь фиксирует изменение identity до конфигурационных
записей. В исправленном повторе оба ответа `*IDN?` совпали: `1.04-0.01`.
Профиль для всех трёх CH прочитан как `VOLT?=1`, `CURR?=0.1`, `VOLT:LIM?=4`,
limit state=1, timer=0, channel output=0; Series/Parallel/Tracking=0, OFF bits=0/0/0.
Все ответы очереди ошибок: `0, "No error"`. PSU meter при выключенном выходе показывал
`MEAS:VOLT?=0.00408745/0.00189686/0 V`, `MEAS:CURR?=0/0/0.000290878 A`; точность
не оценивалась. Оператор подтвердил физические OFF, нагрузку OFF/отсоединённой и
уставки 1.00 V / 0.100 A на всех каналах. H02 — **HW OBSERVED PASS** в этом сценарии;
точность лимитов под нагрузкой и электрическое поведение остаются HW UNVERIFIED.
См. [первая попытка](hardware_reports/2026-10-25T213651.354322Z_H02_qualification.md)
и [исправленный PASS](hardware_reports/2026-10-25T214134.648837Z_H02_qualification.md).
### H03: CH1/CH2 CV/CC прошли review; status CH3 требует диагностики

Первый запуск выполнялся с длинными тонкими проводами и остановился после превышения
допуска напряжения CH1 CC. В CV Keithley измерил 3.99906 V / 0.0978727 A / 0.392112 W,
KEL103 — 3.967 V / 0.099 A / 0.3933 W. В CC Keithley измерил 3.08919 V / 0.249801 A /
0.77151 W, status mask=10 (CC+ON), KEL103 — 3.008 V / 0.250 A / 0.7539 W. Глобальная
команда `OUTP 0` вернула `0, "No error"`, но status остался 10; оператор вручную
подтвердил все OFF. Отношение разницы напряжения к току составило 0.324 Ω и 0.325 Ω;
это указывает на возможное сопротивление проводов/контактов, но остаётся выводом.

После замены на короткие 10 AWG CH1 CV показал Keithley 3.9988 V / 0.0986824 A /
0.39477 W, KEL103 3.998 V / 0.099 A / 0.3982 W. CH1 CC: Keithley 3.01538 V /
0.249777 A / 0.75292 W, KEL103 3.008 V / 0.250 A / 0.7539 W. Status CC был 10;
панель показывала CC. Оператор подтвердил все каналы и KEL103 INPUT OFF. Обе точки CH1
проверены и PASS. На CH2 позднее измерены обе точки, оператор подтвердил оба дисплея.
CV: Keithley 3.9931 V / 0.0986671 A / 0.394513 W, status 9; KEL103 3.9924 V /
0.0999 A / 0.3988 W. CC: Keithley 3.00772 V / 0.249603 A / 0.750575 W, status 10;
KEL103 3.0037 V / 0.2503 A / 0.7518 W. Все ответы очереди ошибок — `0, "No error"`;
после каждой точки оба прибора подтверждены OFF.

CH3 отличается: паспортный предел напряжения 5 V (CH1/CH2: 30 V); установленный
предел 4.00 V / 0.500 A его не превышал. На точке CH3 CV Keithley измерил
3.99326 V / 0.0998173 A, но `STAT:OPER:INST:ISUM3:COND?` несколько раз вернул `8`
(только ON, без битов CV/CC). Руководство определяет этот запрос как condition-регистр
конкретного канала, биты 0/1 — CV/CC, бит 3 — ON. Очередь ошибок оставалась нулевой;
оператор не успел подтвердить режим панели до безопасной остановки. Точка не PASS,
а FAIL/UNVERIFIED. См. [журнал](../reports/hardware/2026-10-25T231834.474816Z_H03/events.jsonl)
и [отчёт H03](hardware_reports/2026-10-25T231834.474816Z_H03_qualification.md).

Read-only preflight KEL103 по UDP/18190 вернул V3.30, INPUT OFF, режим CR и нулевые
измерения. Сетевые записи runner ограничены CR 40/12 Ω и INPUT ON/OFF с обязательным
readback; запись физически проверена на CH2 без ошибок прибора. Диагностический опрос
questionable-status CH3 подготовлен, но ещё не запускался. См. [отчёт H03](hardware_reports/2026-10-25T231834.474816Z_H03_qualification.md)
и [журнал событий](../reports/hardware/2026-10-25T231834.474816Z_H03/events.jsonl).

Руководство Keithley подтверждает: bit 3 означает ON, bit 1/2 — CV/CC. Аварийное
выключение сначала переходит в Remote, запрашивает глобальный OFF, проверяет все каналы
и индивидуально посылает `CHAN:OUTP 0`, если канал остался включён. Полный offline
suite: 56/56 SIM TESTED.
H03 остаётся PARTIAL. Диагностическое дополнение runner записывает CH3 questionable-
condition рядом с operation status и запрашивает подтверждение панели до останова при
несовпадении. Оно не подменяет один регистр другим и не игнорирует несовпадение.
Offline-регрессия прошла 56/56; перед повторной точкой CH3 требуется новый точный допуск.

Последнее продолжение CH3 остановилось до настройки нагрузки и профиля PSU: KEL103
`*IDN?` завершился тайм-аутом. При очистке первой командой Keithley была `OUTP 0` в
режиме Local; следующий `SYST:ERR?` вернул `-200, "Execution error"`. Ответ не указывает
исходную команду. Теперь библиотека посылает `SYST:REM` перед аварийным OFF. Исправление
проверено только симуляцией; см. [отчёт попытки](hardware_reports/2026-10-25T233455.502881Z_H03_qualification.md).

Для KEL103 добавлен явный USB CDC serial путь H03
(`--load-transport serial --load-serial-port /dev/ttyACM0`, 115200 8N1). Он использует
allowlist H03, блокирует дальнейшие команды при неопределённой связи и не переключается
с UDP автоматически. Framing и baud основаны на community-протоколе; KORAD подтверждает
наличие USB, но не публикует протокол на странице продукта. В предыдущей разрешённой
попытке USB вернул KEL103 V3.30 и INPUT OFF; после `:INP OFF` readback также подтвердил
OFF. В следующей разрешённой попытке проверены настройка/чтение CR 40 Ω, управление
INPUT ON/OFF и телеметрия под нагрузкой; это HW OBSERVED, не полный проход этапа.
Очередь Keithley вернула
`170, "Invalid command"` после `SYST:REM`, но очередь не опрашивалась до этой команды,
поэтому источник ответа не установлен. Runner теперь сначала записывает исходную очередь
и запрещает мутации при любой ошибке. Текущая offline-регрессия: 59/59. См.
[карточку H03](H03_PREFLIGHT.ru.md), [отчёт предыдущей попытки](hardware_reports/2026-10-25T235449.217553Z_H03_qualification.md) и [отчёт точки CH3](hardware_reports/2026-10-25T235757.702842Z_H03_qualification.md).

H03 остаётся PARTIAL из-за неквалифицированной status-телеметрии CH3. Последний gated
повтор по USB выполнил обе точки CH3. CV: Keithley 3.99576 V / 0.0998173 A / 0.399012 W (SCPI power);
KEL103 4.0003 V / 0.0999 A / 0.3996 W. CC: Keithley 2.98781 V / 0.249532 A /
0.745347 W (SCPI power); KEL103 2.9840 V / 0.2487 A / 0.7421 W. Оператор подтвердил PSU CV, затем
CC, KEL CR и INPUT ON на соответствующих live gates. Обе электрические точки прошли
допуски H03. Все 192 ответа Keithley `SYST:ERR?` были `0, "No error"`.
В обеих точках `STAT:OPER:INST:ISUM3:COND?` вернул `8` (только ON), а
`STAT:QUES:INST:ISUM3:COND?` вернул `1` (CV) и `2` (CC). Руководство Keithley
определяет биты CV/CC 0/1 в обоих channel summary registers и бит ON 3 в operation
summary. Причина `UNKNOWN` в API локализована: `read_channel()` декодировал режим только
из operation status. Драйвер теперь читает оба регистра, использует документированный
режим, если второй регистр не содержит mode bit, возвращает обе маски в `Reading` и
сообщает UNKNOWN при конфликте. Строгий runner продолжает отдельно фиксировать operation
status. Offline-регрессия прошла 60/60. Физический повтор CH3 подтвердил, что
`read_channel()` теперь возвращает CV/CC из questionable status для обоих режимов; operation
status остаётся `8`, поэтому строгий runner обоснованно оставляет H03 в PARTIAL. Все три
выхода и INPUT KEL103 считаны OFF; оператор подтвердил финальный OFF. См.
