# R5-B — аудит оставшихся SCPI-семейств Keithley 2231A-30-3

**Дата:** 2026-10-31. **Статус:** OFFLINE DOCUMENTATION REVIEW ONLY; NO NEW HW QUALIFICATION, NO SCPI I/O.

## 1. Основание и границы проверки

- Изготовитель: *Keithley Model 2231A-30-3 Triple-channel DC Power Supply Reference Manual*, № 077100401, September 2014, §5, печатные страницы 5-2…5-28. Официальный PDF: https://download.tek.com/manual/077100401_Referencemanual.pdf ; страница производителя: https://www.tek.com/en/tektronix-and-keithley-dc-power-supplies/keithley-2220-2230-2231-series-manual-0 . Руководство описывает **семейства**, а не гарантирует одинаковое поведение прошивки на всех ревизиях.
- Состояние исходников: восстановленный снимок после R4.5-F-K + staged R5-A; `src/keithley2231a/{device.py,profile.py,capabilities.py,service.py,transport.py}`, `docs/SCPI_COVERAGE.md`, `docs/R4_3_RISK_REGISTER.md`, профильные и аппаратные отчёты по STEP, CV/CC и CH1/CH2/CH3.
- Применимость к локальной ветке пользователя: R5-A **ранее передан, но в этой беседе ещё не подтверждён как применённый**. Этот отчёт и инкрементальный патч R5-B рассчитаны на уже применённый R5-A. Никакая локальная рабочая копия пользователя автоматически не меняется.
- Аудит проверяет статическую трассировку каждой строки в документальном реестре к конкретному production-драйверу. Он не исполняет новые команды, не открывает COM-порты, не проверяет реальные физические выходы. `*IDN?` и системные события в архивных данных не заменяют проверки команд, которые никогда не запускались.

## 3. Приоритетные неизвестные аппаратные возможности

| Семейство | Что заявлено в руководстве, и зачем оно полезно | Драйвер сейчас | Решение / приоритет |
| --- | --- | --- | --- |
| `VOLT:TRIGgered[?]`, `CURR:TRIGgered[?]` | Отдельные предварительно заданные V/I-уставки для последующего триггера. Возможен аппаратный переход без длительной передачи серии отдельных команд. | Нет общего безопасного API; capability `hardware_triggered_setpoint` = documented only. | **P1:** сначала OFF-only запросы триггерных уставок, синтаксис и цифровые эффекты через PTY; затем только отдельное разрешение на записи/подачу trigger. |
| `*TRG`, `INST:COUPle[:TRIGger]` | Триггер и выбор каналов-участников. Для будущего верхнего слоя ценно различать instrument-native event от host-планирования. | Заблокировано, нет квалификации задержки/синхронности, нет доказанного восстановления. | **P1 исследование:** firmware uncertainty, право изменения setpoint, physical OFF, latencies/jitter, настройки coupling, безопасное rollback. **Не обещать точную одновременность.** |
| `APPLy`, `APPLy:VOLTage`, `APPLy:CURRent` | Задание одного канала U/I одной командой и/или групповых уставок всех каналов. ### Практическое заключение по ценности

**Не осталось существенных пробелов в базовом управлении тремя каналами:** переключение канала, U/I setpoints, выходы, их состояние, измерения U/I/P, статус CV/CC с оговоркой для CH3, отдельные канальные таймеры, Tracking/Series/Parallel и OFF уже имеют защищённые on-wire маршруты. Наличие метода не означает, что все режимы и каналы исчерпывающе проверены под нагрузкой: H09/H10, ограничения firmware и physical wiring остаются отдельными квалификационными матрицами.

**Больше всего нового потенциала** — в нативном trigger/coupling и, вторично, в групповых `APPLy`. Для gateway/верхнего слоя нужно фиксировать отдельно `instrument_native`, `driver_exposed`, `safe_operating_scope`, `evidence_scope`, `atomicity`, `triggerable_channels`, `latency_tested`, `restoration_semantics`: сегодня API capabilities имеет три первых базовых признака и общий текст constraints, но подробностей пока недостаточно для автоматического выбора аппаратной синхронизации.

## 4. Дефекты актуальности документации / контракта

1. Старый `docs/SCPI_COVERAGE.md` не учитывал `configure_source_step()` и `step_source()` и **фактические** CH1 OFF-only + powered experiments. Исправлено в документальном реестре этого пакета. Никаких новых live прав не предоставлено.
2. Docstring публичного `source_step()` в `device.py` всё ещё описывает `STEP` writes и `UP/DOWN` как запрещённые, хотя защищённые внутренние квалификационные операции теперь есть. **Нужна отдельная документационная корректировка исходного кода** после просмотра точных режимов; в R5-B код не меняется.
3. R5-A capability `source_step_query` имеет `evidence="simulated_only"`, тогда как существует **ограниченное реальное CH1 readback evidence**; одновременно широкое `bounded_hw` для всей функции было бы столь же неверно. Следует разделить наблюдение шага, OFF-only запись и powered mutation на самостоятельные capabilities/qualifications. Не переносить evidence CH1 на CH2/CH3.
4. Для `OUTP:ENABle` руководство показывает синтаксис без аргумента, но указывает `0|1` и пример `OUTP:ENAB 1`; query-форма в показанной грамматике не заявлена. Нельзя конструировать `OUTP:ENAB?` по аналогии. Для `INST:COMB:OFF` в таблице странно описан возврат значения при write-only форме; для `DISP:TEXT?` приведено `Returns None`. Это **неразрешённые неоднозначности мануала**, а не подтверждённые варианты исполнения.
5. **Аппаратный SCPI не гарантирует точность измерения:** 2231A current readback ±(0.2% of reading + 10mA) при указанных условиях; это уже выявлено на ВАХ. Query `FETC` нельзя автоматически назвать синхронной точкой вместе с `MEAS`.
6. `R5-A` capabilities — **статический снимок модели**, не результат real-time `*IDN?` и не заявление о текущем состоянии прибора. Имеющаяся аномалия firmware Aux 1.04/0.01 остаётся отдельной заметкой, а не причиной для автоматического ретрая.

## 5. Предложение последовательности работ — сначала библиотека, затем аппаратные гипотезы

**R5-B (этот пакет):** завершить документооборот 86 семейства, исправить устаревший реестр, зафиксировать риски и roadmap. Документальное изменение не требует HW-тестов.

**R5-C (software-only):** расширить только *метаданные* capabilities так, чтобы внешний менеджер мог различать обычные уставки, trigger-staged setpoints, общие/канальные output modes, методы polling status и native-bulk/host-fallback. Не обещать atomicity/latency до аппаратных испытаний. Убрать некорректные docstrings; добавить строгое тестирование модели, сериализации, backwards compatibility не создавать вокруг устаревшего API.

**R5-D (условно, после явного согласования):** точечный read-only audit `VOLT:TRIG?`, `CURR:TRIG?`, `INST:COUP?` со строгими OFF-only guards и отдельными программными UART-тестами; только затем обсуждать один реальный OFF-only run. Если query-грамматика/firmware не подтверждена — оставить `documented_only` и перейти дальше.

**R5-E (отдельная опция):** если trigger полезен для отдельного верхнего проекта и есть безопасный стенд, подготовить ограниченный операторский аппаратный тест изменения setpoint. Ни `*TRG`, ни `APPLy`, ни `OUTP:ENABle` не должны попасть в обычный bypass-интерфейс просто потому, что они перечислены в руководстве.

**Затем R5/R6 roadmap:** типизированный канальный API, профили/владение соединениями, package/release. ВАХ остаётся примером. MCU gateway и драйверы других моделей остаются в другом проекте, с capability-driven выбором аппаратного и fallback механизмов.
